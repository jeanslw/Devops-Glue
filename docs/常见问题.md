## 首次部署

### Q: 需要什么运行环境？

- **PHP 8.1+**，需开启 `pdo_sqlite` 或 `pdo_mysql`、`curl`、`json` 扩展
- 数据库二选一：SQLite（开箱即用）或 MySQL 8.0+ / MariaDB 10.4+
- 使用 Docker 部署则无需手动安装依赖

### Q: 最快怎么跑起来？

```bash
cp config/.env.example config/.env
# 编辑 .env，至少填一个 Git 平台的 URL 和 Token
composer install --no-dev
php -S 0.0.0.0:8080 -t public/
```

浏览器访问 `http://localhost:8080`，账号密码默认用 `.env` 的 `ADMIN_USER` / `ADMIN_PASSWORD`。

### Q: 用 Docker 怎么部署？

`docker-compose/docker-compose.yml` 提供了含 MySQL 的完整部署方案。

```bash
docker build -t devops-glue .
docker run -d -p 8080:8080 \
  -v $(pwd)/config/.env:/var/www/html/config/.env \
  devops-glue
```

### Q: CI 和 CD 服务怎么一起部署？

CI（devops-glue）和 CD（devops-cd）服务有三种部署方式：

**1. 同主机 — 集中一个 `docker-compose.yml`（推荐）**

`docker-compose/docker-compose.yml` 中已包含注释掉的 `cd-service` 区块。取消注释即可：

```bash
cd docker-compose/
# 编辑 docker-compose.yml，取消 cd-service 段的注释（# cd-service: → cd-service:）
docker compose up -d
```

一键启动 CI、CD、MySQL。两个服务通过 Docker 内部 DNS 访问 `devops-mysql`。CD 的 `.env` 中设置 `DB_HOST=devops-mysql`。

**2. 同主机 — 分开两个 `docker-compose.yml`**

CI 和 CD 各自独立的 compose 文件部署。它们需要共享 MySQL，因此需提前创建共享网络：

```bash
# CI 项目下
docker network create devops-net
cd docker-compose/
docker compose up -d

# CD 项目下
# CD 的 docker-compose.yml 需要引用同一网络：
#   networks:
#     default:
#       name: devops-net
#       external: true
docker compose up -d
```

CD 的 `.env` 中设置 `DB_HOST=devops-mysql`（共享网络下 Docker DNS 可解析）。

**3. 不同主机部署**

CI 和 CD 在不同机器上运行时，MySQL 需映射端口到宿主机：

- CI 宿主机：`docker-compose.yml` 中暴露 MySQL 端口：
  ```yaml
  mysql:
    ports:
      - "3306:3306"
  ```
- CD 宿主机：在 `.env` 中指向 CI 宿主机：
  ```env
  DB_HOST=<CI宿主机IP>
  DB_PORT=3306
  DB_NAME=devops_glue
  DB_USER=root
  DB_PASS=<CI的MYSQL_ROOT_PASSWORD>
  ```
- 防火墙：放行 CD 宿主机访问 CI 宿主机的 3306 端口

### Q: 为什么首页什么都没有？

需要先在管理后台（`/admin`）配置映射关系。首次部署后，访问 `/admin` 登录，点击「自动发现」或手动添加映射。

## 配置与启动

### Q: .env 文件三层加载是什么意思？

加载顺序（后面覆盖前面）：
1. `config/.env` — 基础配置（gitignored，放真实密码）
2. `config/.env.{APP_ENV}` — 环境覆盖（如 `.env.production`）
3. `config/.env.local` — 本地覆盖（gitignored，个人调整）

`APP_ENV=production` 时只加载 `.env`，不需要 `.env.production`。

### Q: 改了 .env 为什么不生效？

- 部分配置（如 `build_mode`、映射数据）首次启动后会写入数据库，后续以数据库为准
- 运行时配置在管理后台修改即可，不需要改 `.env`
- 如果必须从 `.env` 重新加载，删除 `ci_app_settings` 表中对应行，重启服务

### Q: 启动报 `DB_DRIVER 必须设为 sqlite 或 mysql`？

`.env` 中 `DB_DRIVER` 未配置或拼写错误。确保值为 `sqlite` 或 `mysql`。

### Q: SQLite 报 `unable to open database`？

`config/data/` 目录没有写入权限：

```bash
# Linux / macOS
chmod 777 config/data/

# Docker
docker exec -it <container> chmod 777 /var/www/html/config/data/
```

### Q: 怎么切换数据库从 SQLite 到 MySQL？

1. 修改 `.env` 中 `DB_DRIVER=mysql` 及 MySQL 连接信息
2. 如果已有 SQLite 数据，需手动迁移（系统不做自动迁移）
3. 首次启动会自动在 MySQL 中创建表（`DB_AUTO_MIGRATE=true`）

## 构建与 CI

### Q: 支持哪些 CI 系统？

支持 **Jenkins** 和 **GitLab CI**，可在管理后台切换 `build_mode`：

- `jenkins` — 仅 Jenkins
- `gitlab_ci` — 仅 GitLab CI
- `both` — 两者同时可用

### Q: build_mode 切换后不生效？

检查每个映射项的 `build_provider` 字段是否与实际构建系统一致。映射表里的 `build_provider` 决定了该项目走哪个 CI 系统。

### Q: 报 `Build 系统 'xxx' 未配置` 怎么办？

`build_mode` 选择了某个系统，但对应的环境变量未配置：
- `jenkins` / `both` → 需要 `JENKINS_BASE_URL`
- `gitlab_ci` / `both` → 需要 `GITLAB_BASE_URL` + `GITLAB_TOKEN`

### Q: 触发构建报 504 超时？

Jenkins 触发构建有超时限制，默认 300 秒（`BUILD_TIMEOUT`）。如果 Jenkins 响应慢，适当增大这个值。

### Q: Pipeline 列表为空？

- Jenkins：检查 Job 是否存在，有无运行过的构建
- GitLab CI：检查项目路径和权限是否正确
- 确认映射表中的 `job_name` 或 `current_path` 与实际一致

### Q: Jenkins 和 GitLab CI 同时支持是怎么工作的？

系统通过 `BuildProvider` 接口抽象了两者的差异。`ci_job_git_map` 表中每条记录指定 `build_provider`，API 调用时自动路由到对应的构建引擎。

### Q: Jenkins Job 怎么配置才能支持参数化 Git 分支？

通过构建参数传递分支信息给 Jenkins。你的 Jenkins Job 需要做以下配置：

1. **安装 Git Parameter 插件**（如果尚未安装）
2. 在 Job 配置中，添加 **Git Parameter** 构建参数：
   - Name：如 `branch` 或 `git_branch`
   - Parameter Type：`Branch`
   - Default Value：`master`
3. 在 **Source Code Management → Git → Branches to build** 中设置：
   - Branch Specifier：`${branch}`（填你的参数名）
4. 在 Git Parameter 的 **Advanced** 设置中：
   - Branch Filter：`origin/(.*)`

这样 Jenkins 就会按传入的参数构建对应分支，而不是固定分支。devops-glue 触发构建时，会把选择的分支作为参数值传入。

### Q: 触发构建报"分支未找到"？

- 确认 Jenkins Job 已安装并配置了 Git Parameter 插件
- 确认 Jenkins Job 中的参数名与 devops-glue 传递的参数名一致
- 确认 Branch Filter 正则表达式正确：`origin/(.*)` 可匹配所有远程分支

## 映射管理

### Q: 什么是「映射」？

映射是 Jenkins Job / GitLab CI 项目 与 Git 仓库、Harbor 镜像仓库之间的关联关系。核心表 `ci_job_git_map`，管理后台可视化编辑。

### Q: 手动添加映射要填什么？

| 必填项 | 说明 |
|---|---|
| Job 名称 | Jenkins Job 名或 GitLab CI 项目完整路径 |
| Git 平台 | gitlab / github / gitee / gitea |
| Build Provider | jenkins / gitlab_ci |
| Git 远程地址 | 仓库 HTTP/SSH 地址 |
| Git 仓库路径 | 如 `tools/my-project` |
| Harbor 仓库 | 格式 `project_name/repo_name` |

### Q: 「自动发现」能做什么？

扫描当前构建模式下所有项目，自动提取 Git 仓库信息，一键导入到 `ci_job_git_map`。
- **Jenkins 模式**：扫描所有 Job，解析 SCM 配置提取 Git 信息
- **GitLab CI 模式**：通过 GitLab API 扫描所有项目仓库
- **both 模式**：同时扫描两者

### Q: 项目找不到对应映射？

- 确认 `job_name` 或 `current_path` 与实际完全一致
- 确认映射状态为 `active`
- 确认 `build_mode` 对应正确（如当前模式是 `jenkins`，则不会返回 `build_provider=gitlab_ci` 的映射）

### Q: 映射修改后为什么不生效？

映射列表有 30 秒缓存（`cache` 表，key=`map_list_{mode}`）。等待 30 秒后自动刷新，或切换到 `gitlab_ci` 模式（该模式跳过缓存）。

## 认证与权限

### Q: 默认账号密码是什么？

`.env` 中 `ADMIN_USER` / `ADMIN_PASSWORD`。首次启动时自动创建用户写入 `admin_users` 表，后续以数据库记录为准。

### Q: 登录一直 401 怎么办？

`.env` 的 `ADMIN_PASSWORD` 和数据库中 `admin_users` 的密码不一致。

**解决方法：**
- 删除 `admin_users` 表中所有行，重启服务，系统会用 `.env` 重新创建
- 或在管理后台（如果能登录）修改密码

### Q: Token 怎么获取和续期？

登录接口 `POST /api/admin/login` 返回 64 位 hex token，24 小时有效。过期后重新登录即可。修改密码会清除所有旧 token。

### Q: 有哪些角色？（v2.4.1）

系统采用基于角色的访问控制（RBAC）。只有一个内置系统角色：

| 角色 | 类型 | 可编辑 | 说明 |
|---|---|---|---|
| `super_admin` | 系统角色 | 否 | 全部 CI/CD 功能，包括用户和角色管理 |

其余所有角色均由管理员自行创建。管理员可以自由创建任意数量的角色并分配权限。

### Q: 权限怎么分的？

权限分为 **CI** 和 **CD** 两大类，支持两级层级：

**CI 权限（8 个，无层级）：**
- 管理后台完整访问、用户管理、管理管理员账号
- 编辑映射、编辑平台版本、修改构建模式
- 自动发现、触发构建

**CD 一级权限（8 个，对应顶层菜单）：**
- 构建管理、部署管理、服务器管理
- Web Shell、部署记录、镜像仓库
- 资源监控、通知管理

**CD 二级权限（7 个，对应子菜单）：**
- 部署：部署到单机、部署到 Docker、部署到 K8S
- 监控：应用资源、系统资源、自定义资源、告警规则

总计 **23 个权限**。权限列表是数据驱动的——新增权限只需在 `permissions` 表中插入一行，无需改代码。

### Q: 什么是「权限隐含关系」？

部分父权限会隐含其子权限。目前：

- `cd.build-manage`（构建管理）→ 自动拥有 `ci.trigger`（触发构建）

当你给某个角色分配「构建管理」时，该角色用户自动获得触发构建的权限。这由 `AppConfig::IMPLIED_PERMISSIONS`（后端）和 `IMPLIED_PERMISSIONS`（前端）共同维护。

### Q: 怎么创建自定义角色？

1. 用 `super_admin` 登录
2. 进入「角色管理」（仅 super_admin 可见）
3. 点击「创建角色」，填入角色标识和显示名称
4. 勾选希望授予的权限
5. 保存 — 角色立刻出现在角色列表和用户创建下拉中

### Q: 为什么 super_admin 不能编辑或删除？

`super_admin` 是系统角色（`is_system=1`）。系统角色：
- UI 上显示锁图标，不可编辑、不可删除
- 权限为 `'*'` 通配符（始终拥有全部权限，不需要列出 23 个）
- 显示名称走 i18n（`user.role_super_admin`），不存数据库

### Q: 角色栏显示 `user.role_xxx` 而不是中文名？

系统角色的显示名来自 i18n 翻译键（`user.role_{角色名}`）。如果看到 `user.role_builder` 这种原始键，说明翻译缺失，需要在 `lang/zh_CN/messages.php` 和 `lang/en/messages.php` 中补充对应的翻译键。自定义角色使用数据库中的 `description` 字段显示。

### Q: `/api/admin/me/permissions` 有什么用？（v2.4.1）

`GET /api/admin/me/permissions` 返回当前用户的角色和权限列表。只需要有效的 Bearer token，不需要 admin 权限。

返回格式：
```json
{
  "role": "builder",
  "permissions": ["ci.trigger", "cd.build-manage"]
}
```

`super_admin` 的 `permissions` 为 `"*"`（通配符，表示所有权限）。

### Q: CD 怎么检查用户权限？

CD 前端调用 `GET /api/admin/me/permissions` 获取当前用户权限，然后判断是否包含某个权限键：
```js
var perms = await fetch('/api/admin/me/permissions');
if (perms.permissions === '*' || perms.permissions.includes('cd.deploy.k8s')) {
    // 显示 K8S 部署按钮
}
```

### Q: 如何创建新管理员？

1. 用 super_admin 账号登录管理后台
2. 进入「用户管理」→「创建用户」
3. 填入用户名、密码，选择角色
4. 只有 `super_admin` 能管理用户和角色

### Q: Swagger UI (/api/docs) 打不开？

文档页面需要认证。访问 `/api/docs` 会自动跳转登录页。如果 `.env` 中 `ADMIN_PASSWORD` 为空则直接放行。

## Harbor 与安全扫描

### Q: Harbor 扫描同步（scan-sync）是什么流程？

1. 从 Harbor 获取指定 tag（或最新 tag）的漏洞扫描报告
2. 将扫描结果回写到 Git 平台的 Commit Status（状态：`harbor-scan`）
3. 记录到 `ci_pipeline_tags` 表（tag → pipeline 映射）

### Q: scan-sync 报 `tag 在 Harbor 中不存在`？

- 确认该 tag 确实已推送到 Harbor
- Harbor 中的 tag 名区分大小写
- 如果 Harbor 不可达，系统会降级放行（不阻塞 CI 流程）

### Q: Harbor 仓库格式是什么？

`harbor_repository` 必须为 `project_name/repo_name`（以 `/` 分隔的两段）。如 `myteam/myapp`。

### Q: Harbor 扫描显示 pending？

可能原因：
- Harbor 未配置漏洞扫描器（Trivy、Clair 等）
- 扫描正在进行中
- Harbor 服务不可达

### Q: 除了 Harbor 扫描，还支持哪些安全扫描？

通过 Commit Status 端点（`POST /api/build/{path}/commit-status`），CI pipeline 中的任意扫描步骤都可以回写结果：

- **密钥扫描**：Gitleaks、TruffleHog（context: `secret-scan`）
- **SAST**：SonarQube、Semgrep（context: `sast`）
- **依赖扫描**：Trivy、Snyk（context: `sca`）
- **IaC 审计**：Checkov、tfsec（context: `iac-audit`）

所有扫描记录统一存储在 `ci_security_checks` 审计表。

## 数据库与性能

### Q: 改表结构要注意什么？

⚠️ **必须四处同步更新**：
1. `config/AppConfig.php` → 新增对应 `TABLE_*` 常量
2. `src/Service/Database.php` → `ensureTables()` 方法（自动迁移逻辑）
3. `database/mysql_init.sql` → MySQL 手动建表脚本
4. `database/sqlite_init.sql` → SQLite 手动建表脚本

新增一张表（如 `ci_new_table`）的流程：
1. 在 `AppConfig.php` 中定义 `TABLE_NEW_TABLE = 'ci_new_table'`
2. 在 `ensureTables()` 中添加 `CREATE TABLE IF NOT EXISTS`，通过常量引用表名
3. 同时在两个 `.sql` 初始化脚本中添加相同的 `CREATE TABLE` 语句

`ensureTables()` 中已有的 `ALTER TABLE` 加列或 `CREATE INDEX` 加索引不需要同步到手动脚本，但新建表必须四处同步。

### Q: 哪些数据有缓存？缓存多久？

| 缓存项 | TTL |
|---|---|
| 映射列表 (`map_list_{mode}`) | 30 秒 |
| Admin Token (`admin_token_{token}`) | 24 小时 |
| Harbor API 版本探测 (`harbor_api_version`) | 1 小时 |

### Q: 健康检查 `/api/health` 响应慢？

默认对外部服务的超时为 3-5 秒。如果某个外部服务响应慢，可能导致整体健康检查超过 3 秒。

**解决：** 检查网络连通性，确认所有配置的 `BASE_URL` 均可访问。

### Q: MySQL 连不上 / Access denied？

- 确认 `DB_HOST`、`DB_PORT`、`DB_USER`、`DB_PASS`、`DB_NAME` 正确
- 确认 MySQL 用户有建表权限（`DB_AUTO_MIGRATE=true` 时）
- Docker 环境注意网络模式，容器内 `127.0.0.1` 指向容器自身而非宿主机

### Q: 表不存在的报错？

`DB_AUTO_MIGRATE=false` 且未手动执行建表脚本。运行 `database/mysql_init.sql` 或 `database/sqlite_init.sql`，或将 `DB_AUTO_MIGRATE` 设为 `true`。

## Git 平台对接

### Q: git_platform 如何自动检测？

从 `git_remote` URL 的域名自动匹配（关键词：gitlab, github.com, gitee.com 等）。如果自动检测失败，手动在映射中指定 `git_platform`。

### Q: 支持哪些 Git 平台？

GitLab、GitHub、Gitee（码云）、Gitea，支持自定义扩展。

### Q: 如何对接自建 GitLab/Gitea？

在 `.env` 中配置对应平台的 `BASE_URL` 和 `TOKEN` 即可：

```ini
GITLAB_BASE_URL=https://gitlab.yourcompany.com
GITLAB_TOKEN=glpat-xxxx
GITEA_BASE_URL=https://git.yourcompany.com
GITEA_TOKEN=xxxx
```

映射中 `git_platform` 填写 `gitlab` 或 `gitea`。

### Q: Gitee 为什么不支持 Commit Status？

Gitee 公开版 API 不支持 Commit Status 接口（返回 405）。如需此功能，考虑使用 Gitee 企业版或其他平台。

### Q: `DEFAULT_GIT_PLATFORM` 什么时候生效？

当 `git_remote` URL 无法被任何已注册 Provider 识别时，回退到 `DEFAULT_GIT_PLATFORM`。

### Q: 健康检查页面的「Git 运行时连通性」到底监控什么？

它监控的是 **Git 运行时连通性**，不是集成状态。只回答一个问题："系统能否正常访问当前映射关系所引用的 Git 平台 API？"

检查链路：

```
ci_job_git_map.git_platform（如 "gitee"）
        ↓
匹配配置 → api_base_url（如 "https://gitee.com/api/v5"）
        ↓
HEAD 请求 → HTTP 200 = 可达
```

**它检查的：** 到 Git 平台 API 的网络连通性。

**它不检查的：**
- Token 是否有效 / 认证状态
- 仓库是否存在
- Webhook 是否正确配置
- Jenkins 能否 clone 该仓库

三种状态的含义：

| 状态 | 含义 | 显示 |
|---|---|---|
| `null`（无映射引用任何平台） | 无运行时引用，跳过检查 | ⚪ 无运行时引用 |
| `true`（HEAD 请求成功） | API 地址连通 | ✅ API 可达 |
| `false`（HEAD 请求失败） | API 地址不可达 | ❌ API 不可达 |

如果 `ci_job_git_map` 没有记录引用该 Git 平台，则显示「无运行时引用」——这**不是**平台没配好，只是当前没有映射用到它。

## 国际化

### Q: 如何切换语言？

- **界面**：右上角语言选择器（`中文 / English`）
- **URL 参数**：`?lang=zh_CN` 或 `?lang=en`
- **浏览器**：自动检测 `Accept-Language` 请求头
- **存储**：前端使用 `localStorage('dg_lang')` 记住选择

### Q: 支持哪些语言？

中文（`zh_CN`）和英文（`en`）。

### Q: 如何添加新语言？

1. 在 `config/AppConfig.php` 的 `SUPPORTED_LOCALES` 中添加语言代码
2. 在 `lang/` 下创建新语言目录（如 `lang/ja/`）
3. 翻译 `messages.php` 中所有键值
4. 前端 `public/assets/i18n.js` 添加对应语言包

### Q: 国际化会影响 API 吗？

不会。API 响应仍返回原始数据，国际化仅影响前端界面和控制器的错误消息提示。
