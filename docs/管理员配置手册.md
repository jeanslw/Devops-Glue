## 1. 概述

Devops-Glue API 是基于 Slim4 的统一 API 层，为 Jenkins / GitLab CI 拉取式构建 + Custom_Push 推送式构建（理论上支持所有 CI）、GitLab / Gitee / GitHub / Gitea 多平台代码、以及 Harbor 镜像仓库提供统一管理入口，覆盖从 CI 到 CD 的完整流程。它本身是 CI 增强组件，完整系统需配套部署服务 [Devops-Glue CD](https://gitee.com/jeanslw/devops_cd)。

| Devops-Glue API | Devops-Glue CD |
|:---:|:---:|
| v2.6 | v1.4 |
| v2.5 | v1.3 |
| v2.4 | v1.2 |

> 版本对应关系：Devops-Glue API v2.6 对应 CD v1.4，v2.5 对应 CD v1.3，v2.4 对应 CD v1.2。可在管理面板「对接版本」页查看各平台的 API 版本。

## 4. 配置环境变量

```bash
cp config/.env.example config/.env
```

编辑 `config/.env`，至少填写以下关键项：

- **CI 系统**：`JENKINS_BASE_URL` / `JENKINS_USER` / `JENKINS_TOKEN`
- **Git 平台**：`GITLAB_BASE_URL` / `GITLAB_TOKEN`（以及 `GITHUB_*` / `GITEE_*` / `GITEA_*` 按需）
- **Harbor**：`HARBOR_BASE_URL` / `HARBOR_USER` / `HARBOR_PASSWORD`
- **管理后台**：`ADMIN_USER` / `ADMIN_PASSWORD`（首次启动创建根管理员账号）
- **数据库**：`DB_DRIVER` / `DB_HOST` / `DB_PORT` / `DB_NAME` / `DB_USER` / `DB_PASS`（MySQL 时）

完整的环境变量清单与说明见 [附录 A](#附录-a环境变量完整参考)。

## 5. 准备数据库

支持两种数据库，由 `DB_DRIVER` 决定：

- `DB_DRIVER=mysql`：Docker Compose 会自动启动 MySQL 8.4 并创建数据库，同时完全兼容 MariaDB 10.4+。需在 `.env` 填写 `DB_HOST` / `DB_PORT` / `DB_NAME` / `DB_USER` / `DB_PASS`。
- `DB_DRIVER=sqlite`：数据文件位于 `config/data/data.db`，无需额外数据库服务。生产环境建议使用 MySQL/MariaDB。

`DB_AUTO_MIGRATE` 控制建表方式：

- `true`（默认）：首次启动自动建表 + 写入种子数据。
- `false`：手动执行 `database/` 下的初始化脚本（`mysql_init.sql` 或 `sqlite_init.sql`），启动时仍会自动补种子数据。

## 7. 首次启动与自动初始化

首次启动时，系统会自动完成以下初始化：

1. **建表**：创建权限、角色、映射、用户、API Token 等全部数据表（`DB_AUTO_MIGRATE=true` 时）。
2. **种子数据**：写入内置权限、隐含规则、系统角色 `super_admin`。
3. **根管理员账号**：读取 `.env` 中的 `ADMIN_USER`（默认 `admin`）与 `ADMIN_PASSWORD`，创建拥有全部权限的 `super_admin` 账号。
4. **构建模式种子值**：读取 `BUILD_MODE`（默认 `both`）。

> 未设置 `ADMIN_PASSWORD` 时视为首次初始化，不会创建管理员账号，登录前需先在 `.env` 中设置密码。

## 9. 接入 CI 平台

Devops-Glue 通过两种互补方式接入 CI，**理论上支持所有 CI 系统**：内置拉取式（Jenkins 与 GitLab CI）与推送式 Custom_Push（任意 CI 脚本均可上报构建结果）。

**Jenkins**：在 `.env` 填写

```ini
JENKINS_BASE_URL=http://your-jenkins:8080
JENKINS_USER=admin
JENKINS_TOKEN=your_token
```

**GitLab CI**：复用 GitLab 平台配置（见下一步）。

配置完成后，在「监测概览」页确认服务连接正常。

## 10. 接入 Git 平台

在 `.env` 按需填写各平台的 `BASE_URL` 与 `TOKEN`：

```ini
GITLAB_BASE_URL=http://your-gitlab
GITLAB_TOKEN=your_token

GITHUB_BASE_URL=https://api.github.com
GITHUB_TOKEN=your_token

GITEE_BASE_URL=https://gitee.com/api/v5
GITEE_TOKEN=your_token

GITEA_BASE_URL=http://your-gitea
GITEA_TOKEN=your_token

DEFAULT_GIT_PLATFORM=gitlab   # URL 无法自动识别时的兜底平台
```

- 系统会根据仓库 URL 关键字自动识别平台；自建 GitLab/Gitea 域名通常缺少平台关键字，会降级到 `DEFAULT_GIT_PLATFORM`，因此建议显式配置。
- 需接入非内置平台时，参见 [附录 D](#附录-d自定义-git-平台接入)。

## 11. 接入 Harbor

在 `.env` 填写：

```ini
HARBOR_BASE_URL=http://your-harbor
HARBOR_USER=admin
HARBOR_PASSWORD=your_password
```

Harbor 用于关联构建产物（镜像仓库），并在安全审计中触发镜像扫描。

> **关于机器人账户（robot account）：**
> Devops-Glue 通过 HTTP Basic Auth 调用 Harbor REST API，因此账号必须能用于 REST API：
>
> | Harbor 版本 | 机器人账户是否可用于 REST API |
> |---|---|
> | v1.x / v2.0.x / v2.1.x | ❌ 不支持。机器人账户令牌为 JWT（legacy），仅可用于 Docker/Helm CLI |
> | v2.2.0+ | ✅ 支持。机器人账户使用 secret，可 Basic Auth 调用 REST API |
>
> - **Harbor ≥ 2.2.0**：`HARBOR_USER` 可填 `robot$xxx`，`HARBOR_PASSWORD` 填创建机器人账户时复制的 secret。
> - **Harbor < 2.2.0**：请使用**普通账户**（用户名/密码）配置 `HARBOR_USER` / `HARBOR_PASSWORD`。
>
> 管理后台「平台对接版本配置」页会实时探测 Harbor 具体版本号，并明确提示当前版本是否支持机器人账户。

## 12. 配置构建模式

在「配置模式」页选择构建模式，取值：

- `jenkins`：仅使用 Jenkins
- `gitlab_ci`：仅使用 GitLab CI
- `both`：Jenkins 与 GitLab CI 并存

该值与 `.env` 中的 `BUILD_MODE` 对应，首次启动以 `.env` 为准，之后可在后台直接切换。

### 拉取式 CI 与推送式 CI

Devops-Glue 的 CI 接入分为两种正交模式：

- **拉取式 CI（Pull）**：由 `build_mode`（`jenkins` / `gitlab_ci` / `both`）控制。Devops-Glue 主动查询 Jenkins / GitLab CI 拉取构建状态、日志与镜像 tag。
- **推送式 CI（Push）**：由 `custom_push_enabled` 独立布尔开关控制。用户在自己的 CI 脚本中触发构建，再主动把构建状态、日志 URL 与镜像 tag 回传给 Devops-Glue。Devops-Glue 仅存储构建元数据与日志 URL 指针，**不参与构建执行**，也**不存储日志内容**。

两者互不影响，可同时启用（例如 `jenkins + custom_push`）。

> **语义说明：** 推送式 CI 复用 `/api/build/{path}/trigger` 端点，但该端点的具体语义由映射表的 `build_provider` 决定——同一个 `{path}` 同一时刻只绑定一个 provider，因此不同场景互不冲突：
>
> | `build_provider` | `/trigger` 语义 | 数据方向 |
> |---|---|---|
> | `jenkins` | Devops-Glue 主动调用 Jenkins 触发一次构建 | 出向（Devops-Glue → Jenkins）|
> | `gitlab_ci` | Devops-Glue 主动调用 GitLab 触发一条流水线 | 出向（Devops-Glue → GitLab）|
> | `custom_push` | 用户 CI 上报**构建结果**（并非触发构建） | 入向（CI → Devops-Glue）|
>
> 推送式 CI 完整流程由单个端点组成：`report`（一次性写入终态构建结果 + 镜像 tag，需 `build.report` scope）。

### 启用 Custom_Push

无需改代码，开箱即用：

1. 在「配置模式」页勾选 **Custom_Push** 复选框。该复选框独立于 `build_mode` 下拉框（下拉框仅 `jenkins` / `gitlab_ci` / `both` 三项）。
2. 在 `config/settings.php` 的 `build.custom_providers` 数组中注册 provider。

配置示例：

```php
'build' => [
    'custom_providers' => [
        [
            'name'   => 'custom_push',
            'class'  => 'App\\Service\\Build\\CustomPushBuildProvider',
            'config' => [
                'variables' => [
                    'env'       => ['type' => 'choice', 'choices' => ['dev', 'staging', 'prod'], 'description' => '构建镜像目标环境（可选）', 'required' => false],
                ],
            ],
        ],
    ],
],
```

- `CustomPushBuildProvider` 实现 `BuildProviderInterface`，启动时自动发现并注册。
- `variables` 中定义上报时允许携带的自定义变量；不属于控制字段的额外 JSON 键会被作为自定义变量存入 `variables_json`。
- 构建记录存储于新的 `ci_custom_builds` 表，以 `(job_name, pipeline_iid)` 作为唯一键；`pipeline_iid` 必须为整数。
- 相同 `(job_name, pipeline_iid)` 的重复上报按覆盖（UPDATE）处理，保住原自增 id。

### 上报流程（单次上报）

推送式 CI 的构建数据 **一次性** 上报 —— 终态状态与（成功时的）镜像 tag 一并写入：

| 端点 | 时机 | 必填字段 |
|---|---|---|
| `POST /api/build/{path}/report` | 构建（及镜像产物）完成后 | `pipeline_iid` + `status` + `finished_at` |

> **必填支柱（缺一 → 400）：**
> - `pipeline_iid`：关联键，后端硬校验（缺则 400）。
> - `status`：终态构建结果（`success` / `failed` / `aborted`），后端硬校验（缺或非终态则 400）。
> - `finished_at`：构建完成时间，后端硬校验（缺则 400）。
> - `tag`：镜像 tag，`status=success` 时必填，后端硬校验（success 缺则 400）。

`{path}` 可为映射中的 `job_name` 或 `current_path`，两者都归一化到 `job_name`（映射主键）。所有 JSON 键统一 lowercase snake_case。归一化规则见下文 [推送名称与归一化规则](#推送名称与归一化规则)。

#### `POST /api/build/{path}/report` — 上报终态结果

构建完成（或中止）后调用，直接写入终态（无 `pending`/`running` 中间态）。需 `build.report` scope 的 API Token。

| 字段 | 必填 | 类型 / 取值 | 说明 |
|---|---|---|---|
| `pipeline_iid` | ✅ | 整数 | 流水线 ID，与 `job_name` 共同组成唯一键 |
| `status` | ✅ | `success` / `failed` / `aborted` | 终态构建结果 |
| `finished_at` | ✅ | 时间字符串 | 构建完成时间 |
| `started_at` | | 时间字符串 | 开始时间（可选） |
| `ref` | | string | 分支或引用 |
| `sha` | | string | commit SHA |
| `exit_code` | | int | 退出码 |
| `log_url` | | URL | 日志 URL 指针，Devops-Glue 仅保存链接，不抓取/存储日志内容 |
| `web_url` | | URL | 流水线 Web 入口 |
| `tag` | ✅（success） | string | 镜像 tag，`status=success` 时必填并写入 `ci_pipeline_tags` |
| `harbor_repository` | — | string | Harbor 仓库，由 `job_git_map` 决定（body 传入被忽略），须为 `project/repo` 两段式；上报时校验仓库与 `tag` 均真实存在于 Harbor（任一不存在返回 400） |
| （自定义变量） | | — | 其余 JSON 键存入 `variables_json`（如 `env`） |

> **tag 写入语义：** `status=success` 时 `tag` 与可解析的 `harbor_repository` 必填，写入 `ci_pipeline_tags`（`project`、`pipeline_iid`、`tag`、`harbor_repository`、`finished_at` 作为 `created_at`、`status`），由部署（CD）层读取。非成功构建一律不写 tag，避免部署系统拿到失败构建的 tag。

### 推送名称与归一化规则

`custom_push` 以映射中的 **`job_name`（映射主键，跨 `build_provider` 切换的稳定身份）为规范本地记录键**。无论用户 CI 用哪个名字推送，后端都会归一化到 `job_name`：

| 用户推送的 `{path}` | 落库键（`ci_custom_builds.job_name`） |
|---|---|
| `job_name`（推荐） | `job_name` |
| `current_path` | `job_name`（归一化） |

- 推 `job_name` 和推 `current_path` 会落到**同一条记录**，不会因 Jenkins 命名差异产生两条分裂记录。
- `ci_pipeline_tags.project`（部署层交付依据）同样写入归一化后的 `job_name`，与 CD 侧 `t.project IN (job_name, current_path)` 的 join 语义一致。
- **为什么不用 `current_path` 当键**：jenkins 转 custom_push 时 `job_name ≠ current_path`，若按 `current_path` 落库，改回 jenkins 后同一项目会被当成两条（`project` 裂成 `java/registry` 与 `tools/registry`）。
- 若映射的 `job_name` 为空（正常不会，它是主键），则回退到 `current_path`。

#### Jenkins 转 custom_push

把一条 Jenkins 映射（`build_provider=jenkins`）改成 custom_push（`build_provider=custom_push`）是支持的。**`job_name` 保持不变**（它是映射主键，也是改回 jenkins 时的身份锚点），只需：

1. 把 `build_provider` 改为 `custom_push`；
2. 确认该 Git 项目尚无其他 `custom_push` 映射，避免重复。

不要为了让 `job_name` 与 `current_path` 一致而改写 `job_name`——那会破坏「改回 jenkins」时的身份连续性；后端归一化已保证推 `current_path` 也会落到 `job_name`。

**Java（JDK 11+ `java.net.http`，零第三方依赖）**

```java
import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;

public class ReportBuild {
    public static void main(String[] args) throws Exception {
        String base  = "http://localhost:8080/api/build/myapp";
        String token = "<带 build.report scope 的 API Token>";
        // text block 需 JDK 15+；JDK 11 请改用字符串拼接
        String payload = """
            {
              "pipeline_iid": 12345,
              "status": "success",
              "finished_at": "2026-08-18 18:05:30",
              "started_at": "2026-08-18 18:00:00",
              "ref": "master",
              "sha": "a3f8c1d2",
              "exit_code": 0,
              "tag": "v2.0.0",
              "env": "staging"
            }
            """;

        HttpRequest request = HttpRequest.newBuilder()
            .uri(URI.create(base + "/report"))
            .header("Authorization", "Bearer " + token)
            .header("Content-Type", "application/json")
            .POST(HttpRequest.BodyPublishers.ofString(payload))
            .build();

        HttpResponse<String> response = HttpClient.newHttpClient()
            .send(request, HttpResponse.BodyHandlers.ofString());

        System.out.println(response.statusCode());
        System.out.println(response.body());
    }
}
```

```go
    "bytes"
    "encoding/json"
    "fmt"
    "net/http"
)

func main() {
    base  := "http://localhost:8080/api/build/myapp"
    token := "<带 build.report scope 的 API Token>"

    payload, _ := json.Marshal(map[string]any{ // any 需 Go 1.18+
        "pipeline_iid": 12345,
        "status":       "success",
        "finished_at":  "2026-08-18 18:05:30",
        "started_at":   "2026-08-18 18:00:00",
        "ref":          "master",
        "sha":          "a3f8c1d2",
        "exit_code":    0,
        "tag":          "v2.0.0",
        "env":          "staging",
    })

    req, _ := http.NewRequest("POST", base+"/report", bytes.NewReader(payload))
    req.Header.Set("Authorization", "Bearer "+token)
    req.Header.Set("Content-Type", "application/json")

    resp, err := http.DefaultClient.Do(req)
    if err != nil {
        panic(err)
    }
    defer resp.Body.Close()

    fmt.Println(resp.StatusCode)
}
```

**Drone CI（`.drone.yml` 内嵌上报）**

```yaml
kind: pipeline
type: docker
name: build

steps:
  - name: build
    image: golang
    commands:
      - go build ./...
      - go test ./...

  - name: report
    image: curlimages/curl
    when:
      status: [success, failure]   # 失败也要上报
    environment:
      TOKEN:
        from_secret: glue_token
      BASE: http://glue:8080/api/build/myapp
    commands:
      - |
        STATUS="success"; [ "$DRONE_BUILD_STATUS" = "failure" ] && STATUS="failed"
        curl -X POST "$BASE/report" \
          -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
          -d "{\"pipeline_iid\": $DRONE_BUILD_NUMBER, \"status\": \"$STATUS\", \"finished_at\": \"$(date '+%Y-%m-%d %H:%M:%S')\", \"ref\": \"$DRONE_COMMIT_BRANCH\", \"sha\": \"$DRONE_COMMIT_SHA\", \"tag\": \"v1.0.$DRONE_BUILD_NUMBER\"}"
```

- `pipeline_iid` 用 `DRONE_BUILD_NUMBER`，`ref` 用 `DRONE_COMMIT_BRANCH`，`sha` 用 `DRONE_COMMIT_SHA`。
- `DRONE_BUILD_STATUS` 的 `failure` 需映射为我们的 `failed`。
- `tag` 需替换为实际 push 到 Harbor 的镜像 tag（示例用 `v1.0.$DRONE_BUILD_NUMBER`）。

**TeamCity（Command Line 构建步骤）**

新增一个「Command Line」构建步骤，`Execute step` 选「Even if some of the previous steps failed」（失败也执行），脚本内容：

- `pipeline_iid` 用 `%build.number%`，`ref` 用 `%teamcity.build.branch%`，`sha` 用 `%build.vcs.number%`，Token 用环境变量 `%env.GLUE_TOKEN%`。
- `%teamcity.build.status%` 的 `FAILURE` 需映射为我们的 `failed`。
- `tag` 需替换为实际 push 到 Harbor 的镜像 tag。

### 管理面板与自动发现

## 13. 配置映射

映射管理建立 Job ↔ Git 仓库 ↔ Harbor 镜像 三方关联，是 CI 数据聚合的核心。

### 自动发现

系统会自动扫描已启用的 CI 平台，并将发现的 Job 自动加入映射列表（初始为「待启用」状态，需手动启用）：

- `BUILD_MODE=both`：同时扫描 Jenkins 与 GitLab CI 的 Job
- `BUILD_MODE=jenkins`：仅扫描 Jenkins Job
- `BUILD_MODE=gitlab_ci`：仅扫描 GitLab CI Job

> **注意：** 当 `BUILD_MODE=both` 时，同一 `仓库地址` 可能出现重复条目（Jenkins 与 GitLab CI 各一条）。启用其中一条 pipeline（jenkins 或 gitlab_ci）后，另一条会自动隐藏；恢复为「待启用」状态时，重复条目会再次显示，这是正常逻辑。

### 手动映射

每个 Job 可配置以下字段。仅 `job_name` 为必填，其余字段可省略，由系统自动推导。

| 字段 | 必填 | 说明 |
|---|---|---|
| `job_name` | ✅ | Jenkins Job 或 GitLab CI 项目全路径，如 `"java/registry"` |
| `build_provider` | | CI 系统：`jenkins`（默认）/ `gitlab_ci` / `custom_push` |
| `git_platform` | | **强烈建议**自建实例填写。省略时从 URL 关键字自动识别；自建 GitLab/Gitea 域名通常缺少平台关键字，会降级到 `DEFAULT_GIT_PLATFORM`。可选值：`gitlab` `gitee` `github` `gitea` 或自定义名称 |
| `git_remote` | | 省略时从 Jenkins Job SCM 配置自动获取 |
| `project_id` | | GitLab：省略时通过 API 自动查询；GitHub/Gitee：如已知请填写 |
| `web_url` | | 项目主页链接（仅展示） |
| `current_path` | | 项目路径；省略时从 `git_remote` 自动推导 |
| `harbor_repository` | | 关联的 Harbor 仓库，格式 `"project/repository"`（仅展示） |
| `api_version` | | **仅元数据用途**；不影响实际 API 路由（路由硬编码在各 Service 中） |

### 映射数据

示例（`config/settings.php`）：

```php
'job_git_map' => [
    // 自建 GitLab（域名无平台关键字 → 必须指定 git_platform）
    [
        'job_name'          => 'java/registry',
        'git_platform'      => 'gitlab',
        'git_remote'        => 'http://git.mycompany.com/tools/registry.git',
        'project_id'        => 2,
        'harbor_repository' => 'mycode/code-runtime',
    ],
    // SaaS Gitee（URL 含 gitee.com → 自动识别，git_platform 可省略）
    [
        'job_name'          => 'static',
        'harbor_repository' => 'mycode/static-app',
    ],
],
```

## 14. 权限与角色（RBAC）

Devops-Glue 采用数据驱动的 RBAC，权限键与隐含规则全部存数据库，可在后台直接管理。

### 内置角色与内置权限

- 系统内置唯一角色 `super_admin`，拥有全部权限，**不可删除**。
- 权限分「内置权限」与「注册权限」两类：内置权限随系统种子写入，**不可删除**；注册权限通过「权限注册」添加，**可删除**。
- 除 `super_admin` 外的角色（如 `admin` / `deployer` / `viewer`）由管理员在「角色管理」中自行创建并勾选权限。

### 创建角色与分配权限

1. 进入「用户管理 → 角色管理」，新建角色并命名。
2. 在权限树中勾选该角色可访问的权限。
3. 在「用户管理 → 用户列表」创建用户并分配角色。

### 权限注册

当新增 CD 菜单 / 模块需要新的权限键时，无需改代码，直接在「权限管理 → 权限注册」注册权限键（可指定父级键用于层级展示），注册后即可在角色编辑中勾选。权限列表会显示类型（内置 / 注册）与注册时间。

### 隐含规则

隐含规则定义权限的自动继承关系（子 → 父方向）。例如规则 `cd.bot → cd.notification-manage` 表示：勾选 `cd.bot` 时自动带上 `cd.notification-manage`，从而让对应菜单正确显示。

- 内置隐含规则随系统种子写入，**不可删除**。
- 用户通过「权限管理 → 隐含规则」新增的规则**可删除**。

## 15. 创建 API Token

API Token 供第三方服务（尤其是 Devops-Glue CD）或脚本调用 API 使用，独立于 RBAC 登录体系，直接携带接口权限（Scope）。

进入「API 管理」（需相应权限），创建 Token 时选择所需 Scope：

| Scope | 说明 |
|---|---|
| `main` | 只读：Job 列表、映射、Git 平台、Git 发现 |
| `git` | 只读：Git 分支 |
| `harbor.read` | 只读：Harbor 项目 / 仓库 / 标签 |
| `harbor.scan` | 触发 Harbor 镜像扫描 |
| `build.read` | 只读：构建流水线 / 日志 / 分支 |
| `build.write` | 写：触发 / 重试 / 取消构建 |
| `build.report` | 回写：scan-sync / commit-status / report |

> **注意：**
> - Token 明文只在创建成功时显示一次，请立即保存。
> - `/api/admin/*` 等管理端点一律禁止 API Token 访问（仅 super_admin 交互式登录可用）。

## 附录 C：多环境部署

系统通过 `APP_ENV`（production / staging / development）支持环境隔离：

## 附录 D：自定义 Git 平台接入

无需修改核心源码即可接入任意 Git 平台。

### 1. 编写 Provider 类

在 `src/Service/Git/` 下创建适配器，实现 `GitProviderInterface`：

```php
namespace App\Service\Git;

class BitbucketService implements GitProviderInterface
{
    public function getName(): string { return 'bitbucket'; }
    public function matchUrl(string $url): bool { return str_contains($url, 'bitbucket'); }
    public function getApiVersion(): string { return 'v2'; }
    public function getBranches(string $repository): array { /* 分页拉取分支 */ }
    public function getTags(string $repository): array { /* 分页拉取 tag */ }
    public function setCommitStatus(string $repository, string $sha, string $state, string $context, string $description, string $targetUrl = ''): array { /* 回写 commit 状态 */ }
}
```

> `GitProviderInterface` 共 6 个方法，缺一不可：`getBranches`、`getTags`、`setCommitStatus`、`getName`、`matchUrl`、`getApiVersion`。

### 2. 在 `config/settings.php` 中注册

```php
'git' => [
    'custom_providers' => [
        [
            'class'  => 'App\\Service\\Git\\BitbucketService',
            'config' => [
                'name'         => 'bitbucket',
                'base_url'     => 'https://api.bitbucket.org/2.0',
                'token'        => env('BITBUCKET_TOKEN', ''),
                'api_version'  => 'v2',
                'matcher'      => function (string $url): bool {
                    return str_contains($url, 'bitbucket');
                },
            ],
        ],
    ],
],
```

### 3. 自动发现

无需修改其他源码。系统启动时自动发现并注册自定义 Provider。

> **注意：** 自定义平台不支持独立的 `.env` 变量（如 `BITBUCKET_TOKEN`）。Token 需直接写入 `settings.php`，或自行扩展 `AppConfig`。

### 4. 添加内置平台

如需添加内置平台（GitLab/Gitee/GitHub/Gitea 级别），需修改：

- `src/Service/Git/XxxService.php`（适配器）
- `config/container.php`（ProviderRegistry 注册）
- `config/AppConfig.php`（`getXxxConfig` + `getDefaultApiVersion` + `getGitPlatformsConfig`）
- `config/settings.php` + `settings.example.php`（配置段）
- `config/.env.example`（环境变量声明）
