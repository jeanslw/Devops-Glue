## 1. 应用配置

首次安装并登录后台后（默认地址 `http://localhost:8080/admin`），先做好「连接配置」，让系统能访问你的 Jenkins、各 Git 平台和镜像仓库（Harbor / 标准 `registry:2`）。v2.10.0 起这些凭据统一在后台「系统设置 → 平台管理 → 平台连接配置」页维护（不再写 env，旧 env 值用 `cli/migrate-platform-connections.php` 一次性迁入），本节说明每一项的含义与配置要点。

### 1.1 Jenkins（CI 构建源）

在平台连接配置页的 **Jenkins** 行填写：

- **地址**：Jenkins 的访问地址，例如 `http://your-jenkins:8080`，注意协议和端口要写对。
- **用户名**：一个有足够权限的 Jenkins 账号，建议用专门的机器人账号而非个人账号。
- **Token**：在 Jenkins **个人中心 → 凭据/令牌** 中生成的 **API Token**（不是登录密码），用 Token 访问更安全。

> **配置要点**：Token 与密码不同，请在 Jenkins 里单独生成 API Token；该账号只需「读 Job、列分支、触发构建、查状态」等日常构建权限，不必给管理员权限。

### 1.2 Git 平台

系统支持 GitLab、GitHub、Gitee、Gitea（也可扩展自定义平台）。在平台连接配置页按平台分别填**地址与 Token**：

| 平台 | 含义 | 配置要点 |
|---|---|---|
| GitLab | GitLab 地址与访问令牌 | 自建 GitLab 填写内网地址；Token 用带 `api`/`read_api` scope 的个人令牌 |
| GitHub | GitHub 地址与访问令牌 | 地址默认 `https://api.github.com`；Token 用 Personal Access Token |
| Gitee | Gitee 地址与访问令牌 | 地址默认 `https://gitee.com/api/v5` |
| Gitea | Gitea 地址与访问令牌 | 自建 Gitea 填内网地址；Token 用 Gitea 的 API Token |

> **配置要点**
> - 各平台的 Token 只需「读仓库、列分支、回写 commit 状态」等常用权限。
> - 自建 GitLab/Gitea 的域名通常不含平台关键字，系统可能无法自动识别平台，建议同时在 `config/app.env` 设置 `DEFAULT_GIT_PLATFORM` 兜底（该项仍在 env，不迁库）。

### 1.3 镜像仓库（Harbor / 标准 registry）

在平台连接配置页的**「🐳 镜像仓库」**行先选择**仓库类型**（Harbor 默认；标准 OCI 仓库选 `registry:2`），再填写**地址 / 用户名 / 密码**（标准仓库留空用户名与密码即按匿名拉取）。

- **标准 OCI 仓库（`registry:2`）**：没有机器人账户概念，需要在 API 调用中认证时用 HTTP Basic 用户名 / 密码；不提供漏洞扫描（相关列与操作会自动隐藏）。

选用 Harbor 时支持两种账号，配置要点取决于你的 Harbor 版本：

- **v2.2.0 及之后的「机器人账户 / Robot account」（推荐）**
  - 在 Harbor 项目中创建机器人账户，权限按需勾选（至少要能**读/列 tag**，若要触发扫描则要扫描权限）。
  - 把机器人账户的 **用户名和令牌（Token）** 填到用户名 / 密码两栏。
  - 机器人账户比普通账户更安全，推荐使用。

- **v2.2.0 之前的普通账户 / Regular account（旧版本）**
  - 旧版 Harbor 没有机器人账户，使用普通用户账号。
  - 确保该用户至少对相关项目有「只读（pull / 查看 tag）」权限；若需要触发镜像扫描，则需推送/扫描权限。

> **配置要点**
> - 无论哪种账号，遵循**最小必要权限**原则：日常场景给「读 tag、列项目」即可；只有需要系统帮忙触发漏洞扫描时才给扫描权限，避免给管理员账号。
> - 填写的账号必须能访问系统会用到的所有镜像项目。

## 2. 映射管理

「映射管理」把 **CI 任务（Jenkins Job / GitLab CI / Gitea Actions）** 与 **Git 仓库**、**Harbor 镜像仓库** 三方关联起来。之后系统在「监测」里展示的构建、镜像 tag、扫描结果等，都是基于映射产生的。

### 2.1 自动发现

系统会自动扫描已启用的 CI 平台，把发现到的 Job 加进映射列表（初始状态为「待启动 / Pending」，不会主动启用）。

操作步骤：
1. 侧栏 → **映射管理**。
2. 点「🔍 自动发现 / Discover」按钮，等待扫描完成。
3. 列表出现一批「待启动」记录，找到需要的 Job 点「✅ 启用 / Enable」。

> **要点**：当同时启用多个 CI 源时，同一仓库可能被多个源各自发现（如 Jenkins 与 Gitea 都指向同一仓库）。同一仓库同一时刻只会「启用」一条；启用其中一条后，其它同仓库条目会隐藏，这是正常的去重机制。

### 2.2 手动添加映射

操作步骤：
1. 侧栏 → **映射管理** → 点「➕ 新增映射 / New」。
2. 填写表单：
   - **Job 名称（必填）**：CI 任务的完整路径，如 `java/registry`。
   - **构建源 / Build source**：`Jenkins` / `GitLab CI` / `Gitea Actions` / `Custom_Push`，默认 Jenkins。
   - **Git 平台 / Platform**：`gitlab` / `github` / `gitee` / `gitea`，系统也会从仓库地址自动识别，识别不出时按默认平台兜底。
   - **Git Remote**：仓库地址，省略时从 Job 的 SCM 配置自动获取。
   - **Harbor 仓库 / Harbor repo**：填镜像仓库路径，格式 `项目/仓库`，如 `mycode/code-runtime`。
3. 点「保存」。

> 表单里多数字段可省略，由系统自动推导。唯一必填的是 **Job 名称**。

### 2.3 关联镜像仓库

在映射表单的 **镜像仓库** 一栏填写至少两段的仓库路径（如 `项目/仓库`、`团队/项目/镜像`）。关联后，系统展示该 Job 的镜像 tag 时，会去镜像仓库核对这个仓库的真实 tag 列表。

> **要点**：这里填的仓库必须真实存在于镜像仓库中，且格式为至少两段路径，不得包含 scheme、主机名或端口。关联准确，后面的镜像 tag 关联、回写才正确。

### 2.4 停用 / 删除映射

- **停用 / Disable**：把已启用条目降为「待启动」，不再纳入日常监测。
- **删除 / Delete**：彻底删除该映射。删除前会弹确认框。

每行操作列还有「✏️ 编辑」，可随时修改上述字段。

## 3. 构建模式

这里配置系统「主动去拉取哪些 CI 的构建数据」，以及一些与镜像 tag 相关的选项。

### 3.1 设置三个 CI 源

三个 CI 源通过「✅ 构建模式」多选控制，即 **Jenkins**、**GitLab CI**、**Gitea Actions**，可按需多选：

- ⚡ **Jenkins**
- 🐺 **GitLab CI**
- 🦎 **Gitea Actions**

> **要点**：
> - 勾选后立即生效，系统会去这些平台做自动发现、轮询构建状态。
> - 取消某个源后，已启用但与该源不匹配的映射会自动降为「待启动」（不会删除，之后重新勾选可恢复）。

### 3.2 构建结果的镜像 tag 回写（scan-sync / registry-sync）

当 CI 构建产生镜像并 push 到镜像仓库（Harbor 或标准 registry:2）后，系统可以自动完成两件「回写 / write-back」：

1. **镜像 tag 关联**：系统读取构建流水线与镜像仓库中对应仓库的 tag，把它们关联起来，从而在「监测概览 / 构建记录」里看到「这个 Job、这次构建对应的镜像 tag」。
2. **commit 状态回写**：把回写结果（成功 / 失败 / 未知）作为一条状态写到对应的 Git 仓库 commit 上，这样 CI/代码托管平台能直接看到「镜像回写结果」。Harbor 类型还会读取镜像漏洞扫描报告，结论为成功 / 失败 / 未扫描。

回写端点按镜像仓库类型选择：

| 端点 | 适用镜像仓库 | 是否读取扫描报告 | 审计 check_type |
|---|---|---|---|
| `POST /api/build/{path}/scan-sync` | Harbor | 是 | `harbor-scan` |
| `POST /api/build/{path}/registry-sync` | Harbor、registry:2 | 否 | `registry-sync` |

> **要点**：
> - 这一功能依赖映射正确（见第 2 章）：Job 关联了 Git 仓库与镜像仓库，回写才有对象；`registry_repository` 为至少两段的仓库名（如 `project/repo`、`team/project/image`）。
> - 两个端点都需要 **API Token scope** `build.report`；`scan-sync` 读取扫描报告时另需仓库侧已启用扫描能力。
> - 两个端点共用同一套回写逻辑，差异只在是否读取扫描报告；审计 `check_type` 由所选端点决定：`scan-sync` → `harbor-scan`，`registry-sync` → `registry-sync`。`registry:2` 请用 `registry-sync`——误用 `scan-sync` 也能回写，但审计会误标成 `harbor-scan`。

### 3.3 启用 Custom_Push

**Custom_Push** 是一种**反向模式**：不是系统去轮询 CI，而是你现有的 CI（Jenkins Script / Drone / TeamCity 等）在构建结束后，主动把「构建结果 + 镜像 tag」推送给系统，系统只负责接收和记录。适合已有自己 CI 编排、不希望系统介入触发流程的场景。

启用方法：
1. 侧栏 → **配置模式**。
2. 打开「📤 **启用 Custom_Push**」开关。
3. 由管理员在 `config/settings.php` 的 `build.custom_providers` 中注册自定义推送源（部署/配置时完成）。

> **要点**：
> - 开启后会自动发现为每个 Git 项目生成 `custom_push` 映射候选（初始「待启动」，需手动启用）。
> - 关闭开关后，已启用的 Custom_Push 映射会降为「待启动」。
> - 使用场景：我们已有 Jenkins/Drone/TeamCity 作为构建主干，只希望 Devops-Glue 存一份构建与镜像 tag 记录，供 CD 部署读取。

### 3.4 清理过期的 tag 记录（stale tag）

> **先理解「镜像 Tag 记录的来源与可信度」**，3.4 / 3.5 / 3.6 三个功能是一条流水线上的三道工序：
>
> | 来源 | 说明 | 可信度 |
> |---|---|---|
> | **扫描回写（scan-sync）** | Harbor 镜像扫描完成后由回调明确写入的 tag（见 3.2） | **权威**（canonical），部署层直接消费 |
> | **镜像仓库回写（registry-sync）** | 镜像 push 后由回调写入的 tag（见 3.2；仓库不支持扫描时使用） | **权威**（canonical），部署层直接消费 |
> | **日志推导（log）** | 系统在拉取构建记录时，用「推送成功关键字」从构建日志里**猜**出来的 tag（见 3.6） | **候选**，仅作展示与回填依据 |
>
> 三道工序的闭环：**3.6 关键字**决定日志里「什么算一次成功推送」、产出候选 tag → **3.5 回填**把候选 tag 经镜像仓库验证后提升为权威（仓库明确确认存在才写，不覆盖回写结果）→ **3.4 清理**把镜像仓库侧已删除的权威记录移除，防止部署层读到失效 tag。三者全部以 **镜像仓库为唯一事实源**，开关各自独立、互不依赖。

在「系统设置-平台管理」页有「🧹 **启用清理过期 tag 记录**」开关。

- **解决什么问题**：内部记录里的镜像 tag 会随 Harbor 侧的清理（retention 策略、手工删除）逐渐「悬空」——记录还在，但对应的镜像已不存在。悬空 tag 一旦被部署层读到就是一次必然失败的发布。本功能以 **Harbor 为准**，把内部记录里「在 Harbor 中已经不存在」的镜像 tag 记录清理掉（权威 tag 表与关联的构建日志记录同事务删除，不会清一半）。
- **使用场景**：Harbor 配置了「保留最近 N 个 tag」等 retention 策略、或定期手工清理镜像时，开启它让内部记录始终跟上 Harbor 的实际情况。**没有 retention 的静态仓库可以不开**——内部记录本来就不会悬空。
- **操作方法**：
  - **自动**：打开开关后，系统在处理构建记录的合适时机自动比对清理，无需逐条手动删；
  - **手动**：开关开启后可用「▶ **立即清理一次**」按钮立即执行（等价于跑一遍 `php cli/cleanup-pipeline-tags.php`，供无 cron / 无 CLI 的部署主动触发），结果以操作名 `cleanup_pipeline_tags` 落操作日志。
- **安全边界**：比对时若 Harbor 暂时不可达，该批记录**整体跳过不删**（宁可留着脏数据，也不在信息不全时动手）；字段不全无法验证的记录同样跳过。因此**误删的唯一可能是「Harbor 返回了错误的 tag 列表」**，而正常运维下不会发生。

### 3.5 构建日志回填镜像标签（backfill）

在「系统设置-平台管理」页有「🔄 **启用镜像 Tag 日志回填**」开关与「▶ **立即回填一次**」按钮。

- **解决什么问题**：3.2 的扫描回写要求「Harbor 扫描回调成功到达」，但现实里总有缺口——扫描器没配回调、回调 URL 不通、扫描当时恰好宕机。结果就是：**镜像明明推送成功了，权威记录里却没有 tag**，部署层拿不到这个版本。「回填」把日志推导出来的候选 tag（见 3.6）**经过 Harbor 逐个验证确实存在后**，补写进权威记录——相当于给扫描回写兜底，让「推送成功但回调丢失」的版本不至于从系统里消失。
- **信任边界（为什么敢把它写进权威表）**：只有 **Harbor 明确返回「该 tag 存在」** 才写入数据库——回填数据与扫描回写同一信任级，不是盲目相信日志正则。且**仅当该流水线尚无权威 tag 时才补写**，绝不覆盖扫描回写结果；可重复执行（已回填过的自然跳过）。
- **使用场景**：刚接入平台、历史构建都没有扫描回调时，开启开关 + 点一次「立即回填一次」，把历史版本批量补齐；此后可保持开启让系统自动兜底，也可以只在需要时手动跑一次。
- **结果怎么看**：`回填完成：校验 {checked} 条候选，回填 {promoted} 条；跳过 {skipped} 条（已有 tag）、{unreachable} 条（Harbor 不可达）、{unverifiable} 条（字段不全）`——`promoted` 是真正新写入的；`unreachable` 多为 Harbor 暂时不可达，可稍后重跑；操作以 `tag_backfill` 落操作日志。
- **注意事项**：回填的前提是构建日志里能推导出候选 tag（3.6 的关键字命中）。如果你们的 CI 日志格式特殊导致推导不出，调 3.6 的关键字后再重跑回填。

### 3.6 构建日志镜像关键字

在「系统设置-平台管理」页有「🔍 **构建日志镜像关键字**」输入框（默认 `digest`）。

- **解决什么问题**：日志推导 tag 的最大风险是「把失败的构建当成成功的」——日志里出现镜像地址不等于推送成功（可能是 `docker push` 报错前的回显）。关键字就是**推送成功的判据**：只有构建日志中**先命中该关键字**（视为「推送确实成功了」）且**包含本项目的 Harbor 仓库路径**时，才会进一步提取 `repo:tag` / `-t TAG` 作为候选 tag。默认 `digest` 对应 docker push 成功输出的特征行（`digest: sha256:...`）。
- **配置方法**：多个关键字用 `|` 分隔（任一命中即可），大小写不敏感；**留空 = 不过滤**（只要日志含仓库路径就提取——仅建议在日志里不会出现失败推送回显时使用）。
- **使用场景**：CI 输出格式与标准 docker 不同时（例如自研构建工具的成功标志是 `PUSH OK`），把关键字改成 `digest|PUSH OK` 即可适配；日志回填（3.5）老是 `unverifiable` / 提取不到 tag 时，先检查这里的关键字是否与你们日志的成功输出匹配。
- **它影响谁**：关键字只作用于**拉取式**构建记录的「镜像 Tag」列（即日志推导的候选 tag）；扫描回写（3.2）不经过日志，不受影响。

### 3.7 日志设置（API 调用日志 / 操作日志）

在「系统设置-平台管理」页有「📋 **日志设置**」卡片：**写入级别**、**保留天数**、**定时清理**三项。

- **解决什么问题**：API 调用日志按条写入数据库（每个 API 请求一行），高频调用下表会无限增长，最终拖慢查询、撑爆磁盘。日志设置把「**记什么**」和「**留多久**」变成可调策略，让日志体量与你的审计需求匹配，而不是无条件全量永久保存。
- **写入级别**（只控制 **API 调用日志**的写入范围，文件日志始终全量）：
  | 级别 | 写入范围 | 适合 |
  |---|---|---|
  | 全部（成功+拒绝+失败） | 每个请求都记 | 需要完整审计线索（谁在什么时候调了什么接口） |
  | 仅拒绝+失败 | 只记 401/403/404 等被拒请求与 5xx | **推荐**：审计重点本就是异常调用，成功流量不必占库 |
  | 仅失败 | 只记 5xx | 只关心系统自身故障 |
  | 关闭 | 不写数据表 | 完全不需要 API 级审计时 |
- **保留天数**：90 / 60 / 30 天或自定义（1–3650）。到期记录由**定时清理**每天统一删除——清理**同时作用于 API 调用日志与操作日志**（两者共用这套保留策略）。
- **定时清理开关**：默认开启。关闭后两类日志将**无限保留**，仅建议在有外部归档（如定期导出到日志平台）时关闭。
- **不在清理范围**：**部署日志**（数据归 CD 系统管理）与**构建日志**（CI 源侧数据）不受本设置影响。
- **与操作日志页的关系**：这里的「保留天数 / 清理」决定数据**活多久**；后台「日志中心 → 操作日志」页的筛选功能决定你**怎么查**——查询能力不受写入级别影响（但「关闭」级别下 API 调用日志页自然无新数据可查）。

## 4. 用户管理

「用户管理」用于管理**谁能登录后台、属于哪个角色、能干什么**。它分三块：用户列表、角色管理、修改密码。

### 4.1 创建角色

角色 = 一组权限的集合，把权限配给角色，再把用户放进角色，就完成了授权。

操作步骤：
1. 侧栏 → **用户管理 → 角色管理**。
2. 点「新建角色 / New role」，填角色名称。
3. 在权限列表里勾选这个角色可访问的权限（权限内容见第 5 章）。
4. 保存。

> **要点**：系统内置唯一角色 `super_admin`（超级管理员）拥有全部权限且**不可删除**。其它角色（如 admin / deployer / viewer）由你自行创建与配置。

### 4.2 创建用户

操作步骤：
1. 侧栏 → **用户管理 → 用户列表**。
2. 点「新增用户 / New user」，填账号、密码，并选择所属角色。
3. 保存。

> **要点**：
> - 用户必须分配角色才有对应权限；没有角色的用户在后台看不到相应菜单。
> - 内置的 root 账号受保护，**不可删除、不可修改**。
> - 停用账号后，该用户无法再登录（包括 LDAP 登录）。

### 4.3 修改密码

登录用户可在「用户管理 → 修改密码」里修改自己的登录密码（需输入原密码验证）。

### 4.4 用户停用 / 删除

- **停用 / Disable**：让该账号暂时无法登录，保留记录，之后可恢复。
- **删除 / Delete**：彻底删除该用户。

两个操作都会弹确认框，请勿误操作。

## 5. 权限管理

「权限管理」是比「角色」更底层的一层，管理**权限本身**。它分三块：权限列表、权限注册、隐含规则。

### 5.1 内置数据的作用

系统安装时会自动写入一批**内置权限**（如查看映射、触发构建、查看日志、管理通知等）和**内置隐含规则**。它们的作用是让系统默认可用的功能与权限一一对应，是「开箱即用」的基础。

- **内置权限**在「权限列表」中展示，随系统写入，**不可删除**。
- **内置隐含规则**同样不可删除。
- 权限列表会标注类型（内置 / 注册）与注册时间，方便区分哪些是系统自带、哪些是后来加的。

### 5.2 权限注册

当新增一个后台菜单或功能，需要一个新的权限来控制谁能访问时，**无需改代码**，直接在「权限管理 → 权限注册」注册一个新的权限键（可指定父级权限用于树状展示）。注册后，该权限即可在「角色管理」里被勾选分配。

**使用场景**：团队自行扩展了功能，希望用独立权限控制访问范围时用。

### 5.3 隐含规则

隐含规则定义「勾选 A 时自动带上 B」的自动继承关系（子 → 父方向）。

举例：有一条规则「勾选 `cd.bot` 自动带上 `cd.notification-manage`」。勾选前者后，后者会一起被授予，对应的通知管理菜单能正常显示，省去手动逐个勾选。

**使用场景**：两个权限总是成对出现、应该同时授予时，用隐含规则省事且不易遗漏。用户新增的隐含规则**可删除**，内置的不可删除。

## 6. API 管理

「API 管理」用于给第三方服务或脚本签发 **API Token**（如给 Devops-Glue CD 服务、Jenkins 脚本用）。API Token 独立于后台账号体系，直接携带一组接口权限（Scope），方便按需授权、随时调整、随时撤销。只有 super_admin 能创建 / 编辑 / 撤销 / 删除 Token。

本页还承载 **集成服务** 面板（位于 Token 列表**上方**）：启用集成服务会在此自动签发一枚限定 scope 的服务 Token，禁用即撤销它 —— 两者同屏，token 的来源一目了然。开关就是卡片右侧的「启用」复选框（见 6.5）。

### 6.1 创建 API Token

操作步骤：
1. 侧栏 → **API 管理**。
2. 点「新增 / Create」，填写名称（如 `CD 服务账号` / `Jenkins 扫描回写`）。
3. 按需勾选权限（Scope），并可设置过期时间。
4. 保存。

> ⚠️ **Token 明文只在创建成功时显示一次，请立即复制保存**，之后无法再查看完整 Token。

### 6.2 权限说明

| Scope | 作用 |
|---|---|
| `main` | 只读：Job 列表、映射、Git 平台、Git 发现 |
| `git` | 只读：Git 分支 / Tag（含合并端点 `/api/git/{path}/refs`，供 CD 构建页选 ref） |
| `registry.read` | 只读：Harbor 项目 / 仓库 / 标签；以及 `/api/registry/*` 全部接口（Harbor 与 registry:2 两种类型通用）。CD 服务凭据不含该 scope |
| `harbor.scan` | 触发 Harbor 镜像扫描 |
| `build.read` | 只读：构建流水线 / 日志 / 分支 |
| `build.write` | 写：触发 / 重试 / 取消构建 |
| `build.report` | 回写：scan-sync / commit-status / report |
| `rbac.user.write` | CD 服务账号管理：`/api/rbac/*` 用户与角色的建/读/改/删 |

> **设置建议**：
> - 给第三方服务（尤其 CD）授权时，按它实际要用到的最小范围勾选，不要全选。
> - 需要系统帮忙「扫描回写」时，勾上 `harbor.scan` 与 `build.report`。
> - 过期时间按需设置；永不过期便于长期使用，但要留意安全性。

### 6.3 编辑 Token 的权限（Scope）

授权不是一次性的：**已发出的 Token 也能改权限**，不必重新签发。在「API 管理」列表中找到该 Token，点该行的「✏️ 编辑 Scope」，重新勾选后保存。

1. 列表 → 目标 Token 的「✏️ 编辑 Scope」（已撤销 / 已过期的 Token 同样可编辑）。
2. 勾选 / 取消勾选权限（表单默认按**当前权限**预勾选）。
3. 点「保存」，列表立即刷新为新权限。

要点：

- **只改权限，不换 Token**：Token 明文与摘要都不变，已配到 CD / Jenkins 脚本里的 Token **无需更换**，**下一个请求**起就按新权限校验。
- **典型用法**：临时给回写脚本补 `harbor.scan` / `build.report`，用完再取消勾选收回写权限；或给误授权过多的 Token 收敛到最小权限。
- **至少保留一个权限**：全部取消会被拒绝（提示「请至少勾选一个接口权限」），目录外的值也会被拒绝——避免「以为收回了 / 以为加上了」的静默误判。要让 Token 彻底失效请用「撤销」。
- 每次编辑都会记入**操作日志**（操作名 `update_api_token_scopes`，含保存后的权限清单）。

> 示例：Jenkins 扫描回写脚本的 Token 原本只有 `main`，需要它顺手把扫描结果回写回 Git 时，编辑该 Token 勾上 `harbor.scan` 与 `build.report` 保存即可，脚本里的 Token 完全不用改。

### 6.4 撤销 / 删除 Token

- **撤销 / Revoke**：立即停用该 Token（保留记录与 sha256 摘要），适合「怀疑泄露、暂时停用」。本页不提供「重新启用」入口，因此对**普通 Token** 而言它与作废等价 —— 仍要使用请重新签发一枚并更新调用方配置。
- **删除 / Delete**：彻底删除该 Token 记录（摘要一并消失），不可恢复。
- **集成服务那枚 `cd-service` 是特例**：它的启停完全由「🔌 集成服务」卡片接管，见 6.5 —— **卡片取消勾选 = 冻结**（再次勾选即恢复**同一枚**，CD 无需改配置）；而手工 ⛔ 撤销 / 🗑 删除 = **作废**（再次勾选会**补发新凭据**，需同步更新 CD）。

日常建议：临时停用用「撤销」，明确不再使用则「删除」。

### 6.5 集成服务（自动签发的服务 Token）

Token 列表上方还有一张 **🔌 集成服务** 卡片，当前只有一个服务：`CD 部署服务`。它管的是「是否授权 Devops-Glue CD 与本平台共库运行」：

- **怎么启停**：卡片右侧的 **「启用」复选框**就是开关（与「平台管理」页各功能开关同一交互）——**勾选 = 启用**（同一事务内签发服务 Token），**取消勾选 = 禁用（冻结）**。两个方向都会先弹确认框；取消确认或请求失败会把勾选框退回原状态。
- **状态**：⚪ 未启用（若配套凭据只是随服务冻结，卡片会补一行说明：重新启用即恢复同一枚）/ ✅ 已启用（自动建表）/ ✅ 已启用（手动建表）/ ⚠️ 已启用但凭据已失效（红色；勾选框会自动回到未勾选，见下条）。
- **建表方式（`provision`）**：在**勾选启用的那一刻**按本平台当前**迁移模式**（「数据管理 → 迁移模式」）写入，**之后切换迁移模式不会改变它**；未启用时卡片会提示「启用后建表方式」，即点了启用会写成什么。
- **启用（首次）**：勾选卡片右侧的「启用」并确认后，在同一个事务内签发一枚限定 scope 的**服务 Token**（`build.read` + `build.write` + `git` + `rbac.user.write`，不含任何管理端点权限），明文**仅展示一次**，请粘贴到 CD 的 `CI_API_TOKEN`。启用成功后这枚 Token（名称 `cd-service`）会立即出现在下方列表中。
- **启用（恢复）**：若上一次是「禁用（冻结）」后重新启用，**平台不会重新签发**，而是把同一枚 Token 重新点亮 —— 原明文继续有效，**CD 的 `CI_API_TOKEN` 不需要改**（确认弹窗会以「♻ 恢复」说明，也不会再弹出明文框）。
- **禁用（冻结）**：取消勾选「启用」并确认后，CD 立即拒绝所有请求，配套服务 Token 在同一事务内**被停用**（`enabled=0`）。**停用 ≠ 作废**：凭据记录与绑定关系都保留，CD 的数据表与数据**不会删除**，**重新启用即恢复同一枚 Token**（原明文继续可用，CD 无需改配置）。
- **权限**：本页仅 `super_admin` 可见，启用 / 禁用同样仅 `super_admin` 可执行。
- **凭据被撤销 / 删除后仍可再启用（补发）**：列表里那枚 `cd-service` 若被 ⛔ 撤销（服务仍启用）或 🗑 删除，服务立刻不可用 —— 卡片转为红色「⚠️ 已启用，凭据已失效」，勾选框自动回到**未勾选**态。**重新勾选「启用」并确认，即在同一事务内补发新凭据**（旧凭据保持作废、不会复活），不必先取消勾选再勾选；确认弹窗会以「⓪ 补发」提醒，拿到新明文 Token 后记得更新 CD 的 `CI_API_TOKEN`。
- **想彻底作废 / 换发凭据**：在下方列表里 ⛔ 撤销或 🗑 删除那枚 `cd-service`，再点卡片「启用」即走补发路径签发新 Token（记得同步更新 CD）；**只想临时停用**就用卡片取消勾选（冻结，不动凭据），这样再启用时 CD 什么都不用改 —— 两种动作用错了，代价分别是「CD 要换一次配置」与「旧凭据被复活」。
- 状态接口需 `ci.system` 权限，因此「API 管理」页在仅授予 `ci.system` 的账号上也可能看到卡片信息，但「启用」勾选框一律不显示。
- **CD 的授权自检**：CD 可以不直读共享库，改用窄接口 `GET /api/integration/services/cd` 判断本服务是否被授权、以哪种方式建表（需 `build.read` scope，CD 服务 Token 已包含；未启用返回 200 + `enabled=false`，服务名写错才返回 404 —— 两者不可混同）。两条通道读的是同一份契约数据，切换不影响面板状态显示。

## 7. 后台功能页总览（对接版本 / 安全审计 / 监测概览 / 构建记录 / 平台管理 / 日志中心 / 数据管理）

这几块以**查看**为主，这里简单说明它们各自有什么用。更多细节可参考管理员配置手册。

### 7.1 对接版本

「对接版本」展示系统当前对接的各服务（Jenkins / GitLab / Harbor 等）的版本信息。作用：确认各集成服务是否在兼容范围内，排查「某功能不生效」时先来这里确认版本是否满足。

### 7.2 安全审计

「安全审计」记录系统对镜像做扫描 / 回写的历史记录（时间、项目、类型、状态、镜像 tag、Commit SHA、回写结果等）。作用：追踪每次扫描与 commit 回写的执行情况，出现「扫描反馈没到 Git」时来这里排查。支持按回写状态（成功 / 失败 / 未回写）筛选。

### 7.3 监测概览

「监测概览」是首页看板：展示总映射数、活跃项目数、Git 平台数、镜像仓库数，以及各服务（CI / Git / Harbor）的连接状态。作用：一眼看清系统整体健康度与数据规模。
### 7.4 构建记录


「构建记录」（侧栏 → 构建记录）分为两类：

- **拉取式记录**：系统主动从 Jenkins / GitLab CI / Gitea Actions 拉取到的构建记录，含流水线、状态、耗时、镜像 tag、日志链接等。
- **自定义推送 / 推送式记录**：通过 Custom_Push 由你 CI 主动上报的构建记录。

作用：查看历史构建的最终结果与产物（镜像 tag），是核对「某次构建出了什么镜像」的地方。仅当有相应权限时该菜单可见。

### 7.5 系统设置-平台管理页（配置模式）

> 路径：后台侧边栏「**系统设置** → **平台管理**」（页面 ID：`platform-config`）。整页卡片按角色动态显隐：无对应权限的卡片连容器都不渲染。

本页集中管理「CI 平台对接哪些外部系统、以什么模式跑」。每张卡片的功能与权限门槛如下（与后端接口的实际校验一一对应，勿凭界面推测）：

**① 构建模式（多选）** — `ci.mode.edit`
- 勾选启用哪些构建提供方：`Jenkins` / `GitLab CI` / `Gitea Actions` / `Custom_Push`（推送式 CI，用户 CI 一次性上报构建终态）。勾选即刻生效，写入 `ci_app_settings.build_mode`；映射管理里 `build_provider` 字段按此列表选择。
- **解决的场景**：同一套平台渐进迁移 CI 系统（如 Jenkins → GitLab CI）时，新旧两种 Job 并存、逐个切换，不必停机。

**② 平台连接配置（v2.10.0）** — `ci.platform-config`
- 表格式列出 Jenkins / GitLab / GitHub / Gitee / Gitea / Harbor 六平台的**地址与凭据**，每行一个平台：地址、用户名、Token / 密码。令牌与密码类字段只显示「已配置 / 未配置」状态、不显示明文，留空即保持原值；右上角圆点 + 「✓ 已配置 / ✗ 未配置」表示当前是否配齐；每行带「删除」按钮、页底带「保存」。
- **凭据存 DB（`ci_platform_connections`）并用 `DATA_ENC_KEY` 加密后存入数据库**：此处改动即时写库、即时生效，不需要改 env 或重启。旧版 env 里的连接值用 `php cli/migrate-platform-connections.php` 一次性迁入。
- **解决的场景**：多平台并行时快速增改连接；排查 Webhook / 构建触发失败时先看这里（配了没、值对不对），而不是翻 env 文件。

**③ OIDC / SSO 配置卡（v2.10.0）** — `ci.platform-config`
- 维护单点登录的三项：**issuer**（对外可达的完整 URL，反代后必须显式配置）、**id_token 有效期**（秒）、**客户端白名单**（client_id + redirect_uri + secret + 归属系统 + 启用开关，可增删）。secret 只显示「已配置」状态、不显示明文；启用某客户端时必须同时填 secret 与 redirect_uri，否则保存被拒。
- **存 DB（`ci_app_settings` / `ci_oauth_clients`）并用 `DATA_ENC_KEY` 加密**；旧版 env 值用 `php cli/migrate-oidc.php` 一次性迁入。签名私钥仍在 env / 文件，不在此页维护。
- **要让 Devops-CD 用 Glue 账号登录**：本卡只是四道闸门中的第一道 —— 完整步骤（Issuer、`cd` 客户端、用户「可登录系统」、集成服务、CD 侧 env）与报错对照表见 [9. 让 Devops-CD 用 Glue 账号登录](#9-让-devops-cd-用-glue-账号登录全新库到可用)。

**④ 其余设置卡片** — 各自独立权限
- **构建记录推送白名单**（`ci.build_records.push`）：允许哪些 Job 通过 `POST /api/build/{path}/report` 上报终态——不设白名单时任何 Job 都可上报（推送式 CI 的安全边界）。
- **过期镜像标签清理 / 构建日志回填 / 日志关键字 / 日志设置**等平台级设置卡也在本页（见 3.4–3.7 节）。

### 7.6 日志三页（日志中心组）

> 路径：侧边栏「**日志中心**」组：操作日志 / 构建日志 / API 访问日志。三者数据源不同、字段语义不同，排查问题时的查阅顺序建议：先操作日志定位「谁在什么时候做了什么」，再按时间戳去构建日志或 API 访问日志找对应的技术细节。

**① 操作日志** — `ci.operation_logs`
- **数据源**：`ci_operation_logs` 表，由后端各管理动作自动写入（不可人为伪造——写入方在代码里，不经过任何用户可控参数）。
- **字段**：时间 / 操作人（`root` 等管理员或 `system`——系统级事件如版本跃迁审计、定时任务）/ 操作（`migrate_schema`、`schema_upgrade`、`schema_downgrade`、`rbac_seed_failed`、`backup_database` 等，动作名在界面显示为 i18n 文案）/ 对象 / 详情（JSON：版本跃迁带 `previous→current`、`seed_mode`、`channel`；备份带文件名与字节数）/ IP / 结果（成功 ✅ / 失败 ❌）。
- **筛选**：操作人类型（管理员 / system）、操作名、时间范围。**典型用法**：怀疑库结构被人动过 → 按 `schema_downgrade` 或 `migrate_schema` 筛；怀疑权限种子没播全 → 按 `rbac_seed_failed` 筛。

**② 构建日志** — `ci.build_logs`（与操作日志不同表！）
- 记录 CI 构建的原始输出，按 Job 聚合分页浏览；「日志设置」（3.7 节）控制的保留天数即作用于此处的数据量。
- **镜像标签回填与关键字提取的读取对象也是这里**（见 3.5 / 3.6）。

**③ API 访问日志** — `ci.api_access_logs`
- 记录对外 REST API 的调用流水：时间 / 客户端 / 路径 / 状态码 / 耗时 / 调用方 IP。用于回答「我的下游/机器人最近有没有调 / 失败了几个」；配合限流策略（429）定位滥用方。
- 保留天数同样受「日志设置」控制；`cli/cleanup-api-access-logs.php`（分布式变体的 worker 定时任务）做离线清理。

### 7.7 数据管理页（备份 / 数据表 / 迁移模式）

> 路径：侧边栏「**数据管理**」（页面 ID：`system-info`）。**本页所有按钮均为 `super_admin` 专属**；普通管理员进入只见数据表清单与统计，不见操作按钮。

本页三块内容对应三类不同的运维动作，切勿混用：

**① 系统信息卡（只读，`ci.system` 权限即可看）** — 应用版本 / Schema 版本 / `seed` 版本 / **迁移模式**（`DB_AUTO_MIGRATE` 生效值：自动=应用自己建表；手动=橙字提示「建表由 database/*.sql 或 cli/migrate.php 负责，应用仅补种子」）/ **数据表一致性**（`schema_list_drift`：正常为绿字「一致（与代码中的表定义）」；若红字点名表名，说明该实例代码里「应用表常量」与「数据表清单的探测清单」不同步（升级或手工打补丁绕过了 CI），表现为**清单比真实库少表 / 漏报缺失表**——升级到含修复的版本即可，不影响建表与业务）/ 数据库驱动 / 最近一次结构同步时间。**这张卡是判断"该不该跑迁移"的第一入口**。

**② 数据表清单（只读）** — 18 张业务表逐表探测存在性与行数，快速发现"哪张表缺了"（空库 / 半初始化库的诊断入口）。

**③ 备份与恢复（`super_admin`，写操作）**
- 「备份数据库」：导出式全量备份（zip），写入操作日志；`php cli/backup-db.php --force` 与之等效（cron 场景走 CLI）。
- 「恢复」：**离线操作**——恢复不是在线按钮，产物 zip 需通过服务器侧 `bin/restore.php` 执行（不随镜像发布，防误触）；界面只展示备份产物列表与下载。
- 备份产物默认保留策略与清理见操作日志中的 `backup_database` 条目详情。

**④ 同步库结构（`super_admin`）** — 即 3.4 节的「同步库结构」按钮所在处：建缺失表、补缺失列与索引、按当前代码定义收敛 RBAC 种子（prune）。无 DDL 权限的应用账号点击会得到 409 + 明确提示（改用 `php cli/migrate.php`）。**不要**把「同步库结构」当日常维护按钮反复点——正常升级后它会自动完成（自动建库模式下首请求即执行），人工点击只在显式收敛权限或回滚对齐时使用。

## 8. LDAP 登录

除了内置账号，系统还支持使用企业的 **LDAP / Active Directory** 账号登录后台（自 v2.6.3 起）。本节介绍使用层面怎么用；具体安装配置请管理员参看管理员配置手册。

### 8.1 登录顺序

启用 LDAP 后，登录校验顺序为：**本地账号 → LDAP → 配置兜底**。也就是说：
1. 先用本地 `ci_admin_users` 表中的账号校验；
2. 本地没有 / 失败时，再用 LDAP 校验；
3. 仅在首次部署（`ci_admin_users` 表为空）时回退到 `app.env` 里的兜底账号。

### 8.2 使用前提

- 管理员已开启 LDAP 并完成连接配置（需要 PHP 的 `ldap` 扩展）。
- **你的账号必须先由管理员在系统中绑定**：LDAP 只负责「验证密码对不对」，不会自动创建新账号。只有已在后台绑定 LDAP 的用户名才能登录成功。
- 停用的账号同样无法通过 LDAP 登录。

### 8.3 使用方式

1. 打开后台登录页。
2. 输入**你在 LDAP 中绑定的用户名和密码**（登录的是已绑定账号，而非任意 LDAP 用户）。
3. 登录后，该账号的权限、角色仍以系统内对应的账号为准 —— 也就是说，给 LDAP 用户设置角色权限，和普通用户一样，在「用户管理」里操作即可。

## 9. 让 Devops-CD 用 Glue 账号登录（全新库到可用）

> 适用：Glue 与 Devops-CD 联合部署（CD 的登录方式是「使用 Glue 登录」）。不接 CD 的话本节可以跳过。

### 9.1 先分清「四道闸门」

CD 点登录按钮 → 跳 Glue 授权页 → 回 CD 用授权码换 token → 建会话 → 之后每次请求复核身份。链路上有 **四道**都要过的闸门：

| 闸门 | 在哪里配 | 配错的典型表现 |
|---|---|---|
| ① Glue 的 OIDC 客户端白名单（`cd` 行） | Glue 后台「系统设置 → 平台管理 → OIDC / SSO 配置」 | Glue 授权页 **400「无效的 OAuth 请求」** |
| ② Glue 的 Issuer（对外地址） | 同上（Issuer 输入框） | CD 报 502 / discovery 的 `issuer` 与配置不符（最坏被误诊成「密钥问题」） |
| ③ 登录账号的系统归属 + 角色 | Glue 后台「用户管理」（可登录系统 / 角色） | Glue 登录页 **401 `auth.no_ci_access`**；或 CD 回登录页 `errors.no_cd_access` / `errors.identity_unavailable` |
| ④ CD 的「集成服务」授权 + `CI_API_TOKEN` | Glue 后台「API 管理 → 🔌 集成服务」+ CD 的 `.env` | CD 回登录页 `errors.cd_not_enabled` / `errors.cd_not_deployed` |

**排查第一原则：先看报错出现在哪一侧。** 地址栏在 Glue（`/oauth/authorize`）、报错画在 Glue 登录页上 → 查 ①②③；报错回到 CD 的登录页（`/login?error=...`）→ 查 ③④ 与 CD 自身的 `.env`。

### 9.2 从零开始的五步（每步都带「怎么确认」）

**第 0 步 · 确认 Glue 已在运行**
打开 `http://<Glue>/admin`，能出登录页即可（新库首次启动会自动建表并播种管理员账号）。

**第 1 步 · Glue 后台配 OIDC / SSO**
路径：「系统设置 → 平台管理 → **OIDC / SSO 配置**」。

1. **Issuer**：填 Glue 的**对外可达完整地址**（如 `https://glue.example.com`），**与 CD 的 `OIDC_ISSUER` 完全一致**。
   - ✅ 确认：`curl -s https://glue.example.com/.well-known/openid-configuration | jq .issuer,.jwks_uri` —— 两个值都必须是**外部地址**（不能是 `172.x.x.x` / `devops-glue` 这类内网值）。
   - ❌ 不填：Glue 会按当前请求推导（反代后往往推出内网地址）→ CD 的 discovery 校验不过，且症状很像「密钥不对」。
2. **客户端 `cd` 行**（没有就点「➕ 新增客户端」，`client_id` 填 `cd`）：

| 字段 | 填什么 | 填错的后果 |
|---|---|---|
| Redirect URI | CD 的 `CD_OIDC_REDIRECT_URI` 原值（例 `http://cd.example.com/api/auth/oidc/callback`） | **逐字符**比对（scheme / host / port / path），差一个字符 → 授权页 400 |
| Secret | 与 CD 的 `CD_OIDC_SECRET` 完全一致 | 不一致 → CD 换 token 时 Glue 回 `invalid_client`(401) → CD 报「统一登录服务暂时不可用」 |
| 所属系统 | 填 **`cd`** | 留空会被存成 `ci`，只影响「仅属 CD 的账号」（见 9.3） |
| 启用 | 勾选 | 未勾选 = 客户端不存在 → 同样 400 |

   - 保存时后端会拦：**勾了「启用」但 Secret / Redirect URI 为空 → 400 拒绝保存**（避免「刚启用就被 fail-closed 剔除」）。
   - ✅ 确认：保存后该行显示 Secret「已设置」+ `✓ 数据库` 徽标，列表里能看到 `cd`。
3. **id_token 有效期**：默认 3600 秒，通常不用改。

> 全新库也可以让 env 自动播种（见《常见问题》「全新部署还需要手工跑迁移吗」）。**一旦这一页有人工配置（表里已有任意一行），自动播种就不再介入**，不会覆盖你在这里的改动。

**第 2 步 · 准备一个能登录 CD 的账号**
「用户管理 → 新增用户」时，注意 **「可登录系统」** 这一项：

- 选 **「仅 CD」**（`cd`）或 **「CD + CI」**（`cd,ci`）—— 两者都含 `cd`，都能登录 CD；
- 选 **「仅 CI」**（`ci`）→ CD 登录会被拒：Glue 登录页 401 `auth.no_ci_access`，CD 侧则回 `/login?error=errors.no_cd_access`；
- **角色必须是已存在的角色**：CD 登录后会向 Glue 查 `GET /api/rbac/roles/{role}/permissions`，**角色不存在 = 404 = 拒绝登录**（CD 报 `errors.identity_unavailable`）。给角色改名时记得同步该用户的角色；
- 种子管理员（`ci,cd`）天然可登录 CD，自测时最省事。

**第 3 步 · Glue 后台启用「集成服务」（授权 CD）**
路径：「**API 管理**」页顶部 **🔌 集成服务** 卡片 → 勾选 `CD 部署服务` 的「启用」→ 确认。

- 同一事务内会自动签发一枚限定 scope 的服务 Token（名称 `cd-service`，含 `build.read` / `build.write` / `git` / `rbac.user.write`）；
- **Token 明文只显示一次**，复制到 CD 的 `CI_API_TOKEN`；
- 勾选启用的那一刻，Glue 会按当前迁移模式为 CD 建表（这是 CD 能被使用的前提）；
- ✅ 确认：卡片显示「✅ 已启用」，Token 列表里出现 `cd-service`；
- ❌ 不启用：CD 的部署闸门直接拦下登录，回 `/login?error=errors.cd_not_enabled`；
- 临时停用请用卡片「取消勾选」（冻结：凭据保留，重新勾选恢复**同一枚**，CD 不用改配置）；要作废或换发，就在列表里 ⛔ 撤销那枚 Token 再点「启用」补发新凭据（记得更新 CD）。

**第 4 步 · CD 侧 `.env`（与 Glue 逐一对应）**

```ini
OIDC_ISSUER=https://glue.example.com          # = 第 1 步的 Issuer（逐字符一致）
CD_OIDC_SECRET=<第 1 步 cd 客户端的 Secret>     # 逐字符一致
CD_OIDC_REDIRECT_URI=http://cd.example.com/api/auth/oidc/callback   # = 第 1 步登记的 Redirect URI
CI_API_URL=http://<Glue>/                      # Glue 地址（容器内可用服务名）
CI_API_TOKEN=dg_xxx                            # 第 3 步那枚 cd-service 明文
CD_API_TOKEN=<CI→CD 入站令牌，与 Glue 侧同值>
SECRET_KEY=<openssl rand -base64 32>           # 容器部署必填
DB_DRIVER / DB_HOST / DB_NAME / DB_USER / DB_PASS   # 共库或拆库
```

> **`CD_OIDC_SYSTEM` 不是 CD 的配置项**：CD 代码不读它，写在 CD 的 `.env` 里没有任何作用；它只是 Glue 侧「env → DB 播种」的可选输入（详见 9.3）。
> 缺 `OIDC_ISSUER` / `CD_OIDC_SECRET` / `CD_OIDC_REDIRECT_URI` 任一项：compose 预检会直接中止启动（裸机则在启动日志记 ERROR），登录页会点名缺哪几项（`errors.oidc_not_configured`）。

**第 5 步 · 走一遍并确认**
1. 打开 CD 登录页 → 点「使用 Glue 登录」→ 应 302 跳到 Glue 的 `/oauth/authorize?client_id=cd&...` 并显示**登录表单**（不是 400）；
2. 输入第 2 步的账号 → 成功应 302 回 CD 并进入首页；
3. 失败时按 9.4 对照表定位。

### 9.3 为什么 `CD_OIDC_SYSTEM` 可写可不写？

- 它**不是 CD 侧的配置项**：CD 只读 `OIDC_ISSUER / CD_OIDC_SECRET / CD_OIDC_REDIRECT_URI`（`client_id` 固定 `cd`），写在 CD 的 `.env` 里**没有任何作用**；
- 它是 **Glue 侧**「env → DB 播种」的输入，决定 `ci_oauth_clients` 里 `cd` 行的**「所属系统」**列；运行期的 Glue 也不读它；
- **不配也能登录**，原因有两层：
  1. 自 v2.11.2 起，自动播种与 `cli/migrate-oidc.php` 都会把 `cd` 客户端的所属系统**默认落成 `cd`**（更早的迁移脚本会把空值落成 `ci`）；
  2. 即便这一行落成了 `ci`，只要登录账号的**可登录系统含 `ci`** 就能通过 —— 种子管理员是 `ci,cd`，所以用 admin 登录怎么都能进。
- **真正会踩的场景**：用**仅属 CD 的账号**（可登录系统只有「仅 CD」）去登录一行「所属系统 = `ci`」的 `cd` 客户端 → Glue 登录页 401 `auth.no_ci_access`。解决：把这行的「所属系统」改成 `cd` 并保存即可，**不需要改 env、不需要重启**。
- 结论：新部署**可以完全不配 `CD_OIDC_SYSTEM`**；它只在「希望用 env 播种并显式表达归属」时才有意义。**正确做法是在后台该客户端的「所属系统」字段里设成 `cd`**（DB 优先）—— env 与配置文件的迁移/清理顺序见 [第 10 章](#10-从-env-迁到后台配置ui-为准一步步来)。

### 9.4 症状 → 原因 → 解决（一页对照）

| 现象 | 出现在 | 原因 | 解决 |
|---|---|---|---|
| 400「无效的 OAuth 请求（client_id 或 redirect_uri 不匹配）」 | Glue 授权页 | `cd` 行不存在 / 未启用 / Secret 或 Redirect URI 为空（被剔除）/ Redirect URI 与 CD 发来的不完全一致 | 第 1 步第 2 条 |
| 登录页 401 `auth.no_ci_access` | Glue 登录页 | 账号「可登录系统」不含 `cd`，或该客户端「所属系统」不是该账号的系统 | 第 2 步 / 9.3 |
| 「统一登录服务暂时不可用」+ CD 日志 `token 端点返回 HTTP 500` | CD | Glue 换 token 时 500，多为**签名私钥**问题（`OIDC_RSA_PRIVATE_KEY` 非 PEM / `OIDC_KEY_FILE` 不可读） | 看 Glue 日志（v2.11.2 起 5xx 必记）；按《常见问题》私钥小节修 |
| 「统一登录服务返回服务端错误」（上游 5xx） | CD | 同上；CD 已把「上游 5xx」与「连不上」分开提示 | 查 Glue 侧 ERROR 日志 |
| 「统一登录服务暂时不可用」（连不上） | CD | CD 到 Glue 网络 / DNS / 端口不通，或 discovery 拉不到 | 在 CD 容器里 `curl <OIDC_ISSUER>/.well-known/openid-configuration` |
| 回 `/login?error=errors.no_cd_access` | CD | 账号「可登录系统」不含 `cd`（CD 侧复核判拒） | 第 2 步 |
| 回 `/login?error=errors.identity_unavailable` | CD | 账号在 Glue 已删除 / **角色悬空**（角色被删或改名） | 修正该用户的角色 |
| 回 `/login?error=errors.cd_not_enabled` | CD | Glue 未启用集成服务（未授权 CD） | 第 3 步 |
| 回 `/login?error=errors.cd_not_deployed`（带缺失表名） | CD | 已启用但 CD 的业务表未建齐 | 第 3 步（重新勾选「启用」即建表），或按提示手动建表 |
| 回 `/login?error=errors.oidc_not_configured`（带缺项） | CD | CD 的 `.env` 缺 `OIDC_ISSUER` / `CD_OIDC_SECRET` / `CD_OIDC_REDIRECT_URI` | 第 4 步 |
| 登录成功但立刻 401 / 提示服务不可用 | CD | `CI_API_TOKEN` 错误或已失效 → 身份复核失败 | 回「集成服务」重新取用（勾选「启用」可补发） |

命令行自检三条：

```bash
# ① discovery 的 issuer / jwks_uri 都必须是外部地址
curl -s https://glue.example.com/.well-known/openid-configuration | jq .issuer,.jwks_uri
# ② cd 客户端已登记：授权页应返回登录表单，而不是 400
curl -s -o /dev/null -w '%{http_code}\n' "https://glue.example.com/oauth/authorize?response_type=code&client_id=cd&redirect_uri=http://cd.example.com/api/auth/oidc/callback&scope=openid+profile+email&state=x"
# ③ 集成服务已授权（用 cd-service 的明文 token）
curl -s -H "Authorization: Bearer dg_xxx" http://glue.example.com/api/integration/services/cd | jq .enabled
```

## 10. 从 env 迁到后台配置（UI 为准，一步步来）

> 适用：从 v2.10.0 之前的版本升级，或首次联合部署时不确定「到底该写 env 还是该在后台点」。
> 一句话原则：**连接类配置的唯一权威是数据库 —— 在后台 UI 维护；env 只是旧值的一次性迁移输入**。长期留在配置文件里不但没用，还会在排查时误导人（「我明明改了 env，怎么不生效？」）。

### 10.1 先分清：哪些必须在 env，哪些只在后台

| 配置 | 唯一权威 | 还能写 env 吗 |
|---|---|---|
| Jenkins / Git / Harbor 连接（地址、账号、Token / 密码） | 后台「系统设置 → 平台管理 → **平台连接配置**」（`ci_platform_connections`） | ❌ 运行期不读；仅 `cli/migrate-platform-connections.php` 一次性迁入 |
| OIDC **issuer** / **id_token 有效期** | 后台「**OIDC / SSO 配置**」（`ci_app_settings`） | ⚠️ 别写：DB 有值即用 DB，DB 为空才回退 `OIDC_ISSUER` / `OIDC_ID_TOKEN_TTL` |
| OIDC **客户端白名单**（`cd` / `jenkins` / `harbor` 的 Secret、Redirect URI、**所属系统**、启用） | 同上（`ci_oauth_clients`） | ❌ 运行期不读；仅一次性迁移 / 全新库播种 |
| cd 客户端的**所属系统**（即原先的 `CD_OIDC_SYSTEM`） | 同上，该客户端的「**所属系统**」字段 | ❌ **不要写**：CD 侧不读它，Glue 运行期也不读；**DB 优先** |
| OIDC **签名私钥** | env / 文件（`OIDC_RSA_PRIVATE_KEY` 或 `OIDC_KEY_FILE`） | ✅ 必须：不迁库，多副本要同一把 |
| `DATA_ENC_KEY` / `DB_*` / `SECRET_KEY` / `CI_API_TOKEN` / `CD_API_TOKEN` / `TZ` / `LOG_*` | env | ✅ 必须：这些仍是运行期读取的键 |
| `CD_OIDC_SECRET` / `CD_OIDC_REDIRECT_URI` | Glue 后台是权威；但 **CD 容器也读它们** | ⚠️ 联合部署时**保留**（CD 的 client_secret / 回调地址没有别的来源） |

### 10.2 迁移步骤（按顺序做，做完一步再下一步）

下面是「从更早版本升级」的推荐顺序；**全新库可以跳过第 3 步**（引导时会自动播种）。核心心法：**先在 UI 里把值确认对，再删 env**。

1. **备份数据库** —— 后台「数据管理 → 备份」，或 `docker compose exec web php cli/backup-db.php --force`。迁移要写库，这一步必做。
2. **升级代码**到 v2.10.0+（带 `cli/migrate-*.php`）。此时**先不要动 env**：env 里的旧值正是这次迁移的输入。
3. **跑一次性迁移（可选，幂等、不覆盖已有值）**：

   ```bash
   docker compose exec web php cli/migrate-platform-connections.php   # Jenkins/Git/Harbor 连接 → ci_platform_connections
   docker compose exec web php cli/migrate-oidc.php                   # issuer + 客户端白名单 → ci_app_settings / ci_oauth_clients
   ```
   - 全新库（`ci_oauth_clients` 是空表）**不用跑**：v2.11.2 起引导阶段会按 env 非空值自动播种；表里已有任意一行即不介入（想强制重建，先删掉该行）。
   - 想看到逐项「写入 / 跳过」明细，或升级后 env 里补了新值要并进 DB 时再跑。

4. **在后台逐项核对（关键一步）**——脚本只是把值搬进 DB，**权威从此是 DB**，所以必须用 UI 确认真值：
   - 「系统设置 → 平台管理 → **平台连接配置**」：六个平台的地址 / 凭据是否都在（显示 `✓ 已配置`）；
   - 「系统设置 → 平台管理 → **OIDC / SSO 配置**」：**Issuer** 是 Glue 对外地址、**客户端 `cd`** 的 Redirect URI / Secret / **所属系统** / 启用开关是否都对（Secret 只显示「已设置」是正常的，不回显明文）；
   - 顺手点一次「Devops-CD → 使用 Glue 登录」把链路走通（报错对照 [9.4 对照表](#94-症状--原因--解决对照表)）。
   - 若 UI 里的值不对（例如 Issuer 被写成了内网地址）：**直接在这里改并保存**，不要再回头改 env。

5. **确认 UI 无误后，才清理 env** —— 从 `config/app.env` 与根 `.env` 删掉已迁走的键（`JENKINS_*` / `GIT_*` / `HARBOR_*` / `OIDC_ISSUER` / `OIDC_ID_TOKEN_TTL` 等）。**两个例外要记住**：
   - `CD_OIDC_SECRET` / `CD_OIDC_REDIRECT_URI`：**保留**（联合部署时 CD 容器要读它们）；
   - `CD_OIDC_SYSTEM`：**删掉**（它本来就不该写在配置文件里；归属系统在后台该客户端的「所属系统」字段维护）。
   - 仍被运行期读取、必须保留的键：`DB_*`、`DATA_ENC_KEY`、`OIDC_RSA_PRIVATE_KEY` / `OIDC_KEY_FILE`、`SECRET_KEY`、`CI_API_TOKEN`、`CD_API_TOKEN`、`TZ`、`LOG_*`。

6. **重建容器并回归一次**：

   ```bash
   docker compose up -d --force-recreate web worker
   ```
   逐项验证：后台能登录 → 映射 / 构建页有数据 → 镜像仓库能查询 → CD 能登录。

7. **知道怎么回退**（升级前先记下来）：
   - **issuer / id_token 有效期**：在后台把 Issuer 清空保存（等于删掉该设置行）即回退到 env 值；
   - **客户端白名单**：自 v2.10.0 起**没有 env 兜底**，回退只能在后台重填，或让 env 仍有值时重跑 `cli/migrate-oidc.php`；
   - **连接类**：同理，只能在后台重填，或重跑 `cli/migrate-platform-connections.php`。

### 10.3 常见误判（四条最常踩的）

| 现象 | 原因 | 正确动作 |
|---|---|---|
| 「我改了 `config/app.env` / 根 `.env`，怎么不生效？」 | 该键已迁到 DB，运行期不再读 env | 去后台对应页面改并保存；最多等一个复核窗口（默认 60s）后重试 |
| 「env 里 `OIDC_ISSUER` 填得好好的，CD 还说 issuer 不符 / 400」 | **DB 非空即覆盖 env**：只要后台 Issuer 有值，代码就只用 DB 的值 | 先去后台「OIDC / SSO 配置」把它改成对外地址；DB 为空才会回退 env |
| 「`CD_OIDC_SYSTEM` 填什么都不影响」 | 它唯一的作用是「全新库空表时把 cd 客户端归属系统播种成 `cd`」 | 正常现象：请在后台改该客户端的「**所属系统**」字段 |
| 「只改了后台、没重启容器，会有影响吗？」 | 这些配置每次请求都从 DB 读（带短缓存 / 复核窗口） | 无需重启，保存即生效。需要重建容器的只有「仍被运行期读取的 env 键」（`OIDC_RSA_PRIVATE_KEY`、`DATA_ENC_KEY`、`DB_*` 等） |

**一句话记忆**：连接与 SSO 配置 —— **DB（后台 UI）是唯一权威，环境变量只用于「一次性迁移」和「全新库播种」**；迁移完成后就该清掉配置文件里的这些键（例外：`CD_OIDC_SECRET` / `CD_OIDC_REDIRECT_URI` 要留给 CD 容器读，`CD_OIDC_SYSTEM` 则连 CD 都不读，直接删）。
