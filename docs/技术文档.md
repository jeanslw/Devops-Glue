## 2. 请求生命周期

```
1. public/index.php 加载 vendor/autoload.php
2. Dotenv 三层加载环境变量（详见 §3）
3. 静态文件直出（PHP 内置服务器用，生产由 Nginx/Apache 处理）
4. Database::init() — 惰性初始化 PDO（不连接）
5. DI 容器构建（config/container.php 定义所有服务工厂）
6. Slim App 创建 + 路由注册（config/routes.php）
7. 中间件注册（CORS → 路由 → 错误处理）
8. 请求到达 → 路由匹配 → Controller 方法执行 → 响应返回
```

## 3. 配置系统

### 3.1 环境变量加载（三层覆盖）

```
文件加载顺序（后者覆盖前者）：
1. config/app.env          ← 基础配置（gitignored，放真实密码）
2. config/app.env.{ENV}    ← 环境覆盖（提交 Git，不放密码）
3. config/app.env.local    ← 本地覆盖（gitignored，个人调整）

最终生效优先级（高 → 低）：
app.env.local > 真实环境变量（OS 注入）> app.env.{ENV} > app.env

覆盖规则：
- 第1层 app.env 用 createImmutable().load()（安全加载：变量已存在则不写入，
  让 Docker env_file / shell export / Apache SetEnv 注入的真实环境变量优先）
- 第2/3层 app.env.{ENV} / app.env.local 用 createUnsafeMutable().load()
  ⚠️ 不能用 createUnsafeImmutable()：phpdotenv 的 Immutable 语义是「变量已存在则不写入」
    （RepositoryBuilder::make() → ImmutableWriter），而非「允许覆盖」；凡 app.env 已定义的键
    都会被静默丢弃，表现为「改了 app.env.local 不生效」
- app.env.local 存在时，其中定义的键即为最终值（连真实环境变量也覆盖）
- 加载完覆盖层后按 getenv() 快照回写真实环境变量：ImmutableWriter 判定「已存在」只看
  $_ENV / $_SERVER，当 variables_order 不含 E/S 或值来自 putenv() 时保护不到 OS 变量
- 唯一实现：src/Support/EnvFileLoader.php（Bootstrap 与 bin/cli 脚本共用，避免各入口漂移）
```

**实际使用：**

| APP_ENV | 加载文件 | 说明 |
|---|---|---|
| production | `app.env` only | 默认行为，不需要 `app.env.production` |
| staging | `app.env` → `app.env.staging` → `app.env.local` | `app.env.staging` 通常只放 `APP_DEBUG=true` |
| development | `app.env` → `app.env.development` → `app.env.local` | 同上 |

### 3.2 运行时配置持久化

| 配置项 | 存储位置 | 优先级 |
|---|---|---|
| `build_mode` | `ci_app_settings` 表 | DB > `app.env` (回退) |
| `job_git_map` | `ci_job_git_map` 表 | DB 唯一来源 |
| `platform_versions` | `ci_platform_versions` 表 | DB > JSON > 默认值 |
| Admin Token | `cache` 表 (24h TTL) | DB 唯一来源 |
| Harbor API 版本 | `cache` 表 (1h TTL) | 自动探测并缓存 |

### 3.3 配置读取链路

```
Controller → AppConfig::getXxxConfig()
    → settings.php[$section]
        → $_ENV['XXX']  (由 Dotenv 注入)
```

`AppConfig` 是唯一门面，所有控制器/Service 通过它读配置，不直接访问 `$_ENV`。

### 4.2 数据库同步规则

⚠️ **重要：** 表结构变更必须同时更新四处：

1. `config/AppConfig.php` → 新增对应 `TABLE_*` 常量
2. `src/Service/Database.php` → `ensureTables()` 方法
3. `database/mysql_init.sql`
4. `database/sqlite_init.sql`

### 4.3 数据库备份（Web 端）

后台「系统设置 → 数据管理 → 数据库」卡片提供 **备份数据库** 按钮（仅 `super_admin`），由 `src/Service/DataBackupService` 实现（`bin/` 不随镜像发布，Web 侧不依赖 CLI 备份工具）。

- **驱动**：sqlite / mysql 均可，按当前 `DB_DRIVER` 导出。
- **产物**：启用 CD（共享库存在 `cd_*` 表）时产出两份 zip：`devops-glue_<driver>_<datetime>.zip`（应用表）+ `devops-cd_<driver>_<datetime>.zip`（`cd_*` 表）；未启用 CD 时只产出一份。每份 zip 内含同名 `.sql` 纯数据文件（`INSERT` 语句、不含 DDL），排除 `cache` / `ci_platform_versions`；仅备份、不提供 Web 恢复（恢复 / 迁移仍走 `bin/backup.php` 与 `bin/restore.php`）。
- **目录解析**（`backupDir()`）：优先 `BACKUP_DIR` 环境变量；Docker 内默认 `/data/backups`（compose 卷映射宿主 `./data/backups`）；非 Docker 且未设时落仓库根 `backups/`（与 CLI 默认一致）。目录不存在自动创建，并按驱动前缀滚动留存最近 10 份。
- **端点与审计**：`POST /api/admin/backup`（super_admin 门控），成功后写入操作日志 `backup_database`。
- **权限要求**：同 4.4——MySQL 账户需对共享库有库级（或全局）`SELECT`/`ALL`，否则 `cd_*` 表会被静默漏备（备份前自检会打 WARN）。

### 4.4 数据库备份（容器内定时，CI/CD 分离）

`cli/backup-db.php`（随镜像发布，由 supervisord 的 `db-backup` 循环调度）复用 Web 侧 `DataBackupService`，与后台「手动备份」走同一套逻辑：启用 CD（共享库存在 `cd_*` 表）时产出**两份独立 zip**（CI 应用表 + CD 系统的 `cd_*` 表），恢复一方绝不误碰另一方；未启用 CD 时只产出一份。

- **开关**：根 `.env` 的 `DB_BACKUP_ENABLED`（默认关，未开启时打印跳过并退出 0，不给存量部署突增磁盘写入）；间隔由 `DB_BACKUP_INTERVAL` 覆盖，默认 86400 秒。也可手工跑 `php cli/backup-db.php --force`。
- **产物**：与 Web 端同源（复用 `DataBackupService`，「一样的逻辑」）——启用 CD 时产出 `devops-glue_<driver>_<datetime>.zip`（mode=app，应用表）+ `devops-cd_<driver>_<datetime>.zip`（mode=cd，`cd_*` 表，仅存在 cd 表时写出）；未启用 CD 时只产出一份。每份 zip 内含同名 `.sql` 纯数据文件；两个前缀各自滚动保留最新 10 份；仍无条件排除 `cache`（会话 token 是易失凭证）与 `ci_platform_versions`（派生缓存）。
- **只取基础表**：枚举条件 `table_type='BASE TABLE'`，视图（如 `v_glue_deploy_logs`）不会被当成表导出——否则会生成一条对视图的假 `INSERT`，恢复时必然失败。
- **权限要求**：`information_schema.tables` 只返回当前账户有权限的表。账户必须对共享库持有库级（或全局）`SELECT`/`ALL`，否则 `cd_*` 表会被静默漏备——备份前自检会对此打 WARN（见 `DataBackupService::mysqlVisibilityWarning()`）。Docker 默认的 `devops` 业务账号首启即被授予库级 `ALL`；裸机需自行 `GRANT ALL PRIVILEGES ON devops_glue.* TO 账户;`。
- **恢复**：`php bin/restore.php <devops-glue_*.zip> --yes` 恢复应用表；`php bin/restore.php <devops-cd_*.zip> --yes --cd` 恢复 cd 表（`.zip` 与 `.sql` 输入均支持）。文件 META 的 mode 会校验，CI 备份不能用于 cd 恢复、反之亦然。

> 注：`cli/backup-lib.php` 是 CLI 备份/恢复的共用库（`bin/backup.php`、`bin/restore.php`、`cli/backup-db.php` 共用），随镜像发布；`bin/` 下的离线工具不随镜像发布，但会 require 本库。

### 4.5 同步库结构（Web 按钮 / CLI）

后台「数据管理 → 🗄️ 数据库」卡片的 **🔧 同步库结构** 按钮（仅 `super_admin`）与 `cli/migrate.php` 走同一条 `Database::migrateNow()` 路径，作用是把库结构与内置种子对齐到**当前代码版本**：

- **做什么**：`ensureTables()`（缺失表 `CREATE TABLE IF NOT EXISTS`、`$columnMigrations` 逐列 `ALTER ADD COLUMN`、`createIndex()` 补索引、清已废弃的遗留表 `ci_pipeline_tags`）→ `seedRbac()` / `seedAdmin()` → `verifySeed()` 自检通过后 `markSchemaCurrent()` + `markSeedCurrent()`。
- **不做什么**：不重命名/删除字段，不改字段类型或主键（如 `admin_users.id`），无版本化 up/down、无跨库搬迁——这类「手工迁移」请停机备份后用数据库工具执行（只读预检用 `--dry-run`，不写库）。
- **两条入口的差别**：Web 按钮用**应用自身的数据库账号**执行 DDL，账号缺 `CREATE`/`ALTER` 时返回 **409** + `sys.migrate_denied`（明确提示改用 CLI），失败会写一条 `migrate_schema` 失败操作日志；`cli/migrate.php` 无视 `DB_AUTO_MIGRATE`，可用高权限账号在发布流水线（K8s Job / initContainer、Helm pre-upgrade、Compose 一次性服务）中执行。迁移前可先跑 `php cli/migrate.php --dry-run` 只读预检：打印**将补的表/列**与版本状态、**不写库**（退出码 0=无需迁移、2=需要迁移、1=致命错误），便于流水线"先判断再执行"。
- **登录态限制**：按钮需要登录，而表缺失时登录本身会 500——空库/表缺失场景请用 `php cli/db-init.php` 与 `php cli/migrate.php`，按钮只用于「已能登录、只需对齐结构」。
- **术语**：「同步库结构 / Sync Schema」= 本按钮（与 `cli/migrate.php`）；「数据库迁移 / Database Migration」= 同一动作的 CLI 说法；「手工迁移 / Manual Migration」= 重命名、改类型、删列、改主键、跨库搬迁。
- **降级（回滚）时的种子语义**：记录版本高于代码版本时 `seedRbac()` 自动切到**合并模式（`seed_mode=merge`，只补不删）**——补齐当前代码期望的映射、**保留**新版本授予的映射，避免"回滚顺手把权限收窄"；显式 `cli/migrate.php` / 后台按钮始终按当前代码定义**收敛**（`seed_mode=prune`），即「显式动作＝权威种子」。两种模式都会在日志留 warning（merge 时附带收敛办法）。
- **版本跃迁审计（`ci_operation_logs`）**：两条线，互不重叠、一次事件只一行——
  - **自动引导路径**（无人操作）按方向记：首次 `schema_init`、向前 `schema_upgrade`、回滚 `schema_downgrade`（`result` 依次 `success`/`success`/`failure`），`username`/`operator_type`=`system`、`target`=跃迁前版本、`detail={key,scope(schema|seed),previous,current,seed_mode}`；
  - **显式路径**（后台按钮、`cli/migrate.php`）记的是操作本身 `migrate_schema`（含 `from → to`）。
  同 `(action,target)` 在 10 分钟窗口内去重（web / worker 多进程同时启动不刷屏）；窗口外的再次同向跃迁照记。
- **种子部分失败＝fail-fast**：`seedRbac()` 内任何一行写入失败（权限 / 隐含规则 / 系统角色 / 角色↔权限的写入或清理）都会**汇总后抛异常**（与 `verifySeed()` 同一机制）——不标记版本、下次引导重试，并写文件日志（含前 5 条失败明细）＋操作日志 `rbac_seed_failed`（10 分钟去重）。刻意不"记日志继续"：权限只播一半的表现是「某按钮该显示却没显示」，是最难定位的一类问题。

## 5. 核心业务逻辑

### 5.1 存活/就绪探针
**路由：** `GET /healthz`
**Controller：** `HealthzController::__invoke()`

无需认证的外部探针，供 Uptime Kuma / 云 LB / 容器编排抓取。只做 DB 探活、已应用版本读取与 schema 对齐判定，不探测 Jenkins/Git/Harbor，毫秒级返回。

```
1. DB 探活（Database::createPdo() + SELECT 1）—— db 只表达连接性
   └─ 成功后 Database::schemaState()：一条 SQL 读 schema_version / seed_version，判定 schema_current 与 schema_ahead
   └─ 连接 / 读取任一步抛异常 → ready=false（「连不上」与「连上但版本表缺失=空库未初始化」分别写 error 日志）
2. 仅当 schema_current=false 时：Database::missingTables() 逐表探测，列出缺失的核心表
   （正常路径不跑这 N 次查询，探针保持毫秒级）
3. 汇总
   └─ ready=true  + schema_current≠false → HTTP 200 + status=ok
   └─ ready=true  + schema_current=false → HTTP 200 + status=degraded（版本落后或库比代码新，都不摘流）
   └─ ready=false                        → HTTP 503 + status=degraded（db 字段区分「真宕机」与「连上但空库」）
```

**返回结构：**
```json
{
  "status": "ok",
  "db": true,
  "app_version": "2.8.9",
  "schema_version": "2.8.9",
  "seed_version": null,
  "schema_current": true,
  "schema_ahead": false,
  "auto_migrate": true,
  "time": 1760000000
}
```

- `schema_current`：**只认 `schema_version`**（它只由「执行过 DDL」的路径写入：自动模式 `ensureTables()` 成功，或手动模式跑过 `cli/migrate.php` / 后台「同步库结构」）与 `APP_VERSION` 比较；无 `schema_version` 时为 `null`（未知：不降级也不谎称对齐）。**刻意不用 `seed_version` 回落判 true**——种子（RBAC `INSERT`）补齐不代表业务表新增列已就绪，手动模式升级漏跑 DDL 时种子照样能补齐，回落判 true 会把「新代码 + 旧表结构」谎报成健康。
- `seed_version`：仅 `DB_AUTO_MIGRATE=false` 手动建库模式会记录（自动建库模式为 `null`）；它服务于「避免每请求重复播种」的短路与观测排障。
- `schema_ahead`：**方向位**。`schema_version` 高于 `APP_VERSION`（用 `version_compare`，不是字典序）时为 `true`，即「库比代码新」——典型场景是**代码降级/回滚**；无记录时为 `false`。
  - `schema_current=false` + `schema_ahead=false` → 代码比库新（**没跑结构迁移**）：跑 `cli/migrate.php` 或点「同步库结构」。
  - `schema_current=false` + `schema_ahead=true` → 库比代码新（**已回滚降级**）：先确认是否接受旧代码跑新库，再对齐标记，并复核种子被回退覆盖的影响（见「常见问题 → 回滚/降级指引」）。
- `tables_missing`：**仅在 `schema_current=false` 且确实有缺失表时出现**，列出缺失的核心表名；`schema_current` 为 `true`/`null` 时不探测、不下发该字段。
- `auto_migrate`：当前是否自动建表模式（`DB_AUTO_MIGRATE` 未显式关闭）。
- **为什么版本未对齐不返回 503**：滚动升级期「新代码 + 旧 schema」是预期中间态，**回滚降级**（库比代码新）同理——若一并 503，LB / K8s 会把全部副本摘掉，危害远大于 degraded 本身；监控读 `status` / `schema_current` / `schema_ahead` 字段告警即可。

### 5.2 健康检查
**路由：** `GET /api/health`
**Controller：** `MainController::healthDetail()`
**认证：** 需要 Bearer Token（管理员登录 Token 或任意有效 API Token，无需特定 scope）

**检查流程：**

```
1. Jenkins 检查（仅当 build_mode 含 jenkins；纯 CI 模式返回 null 跳过）
   ├─ 短超时 Client GET /api/json 验证连通性（失败 0.5s 后重试一次）
   └─ 调 getVersion() 获取版本号

2. Git 平台检查
   ├─ 从 job_git_map 收集实际使用的平台
   ├─ 只检查已配置且实际使用的平台
   └─ 对每个平台 API URL 发 HEAD 请求（3s 超时）
       └─ HTTP 状态码 < 500 视为 reachable

3. Harbor 检查（多组件）
   ├─ core:       GET /api/v2.0/projects
   ├─ jobservice: GET /api/v2.0/jobservice/ping（404 仍视为 OK）
   └─ registry:   GET /api/v2.0/registries
   └─ 任一组件 false → harbor: false

4. 统计卡片
   ├─ total_maps:    SELECT count(*) FROM ci_job_git_map
   ├─ active_maps:   count WHERE status='active'
   ├─ git_platforms: count(DISTINCT git_platform)
   └─ harbor_repos:  count(DISTINCT harbor_repository)

5. 汇总判断
   └─ allOk = jenkins && git && harbor
   └─ HTTP 200 (ok) / 503 (degraded)
```

**返回结构：**
```json
{
  "status": "ok",
  "checks": { "jenkins": true, "jenkins_version": "2.555.3", "git": [...], "harbor": true, "harbor_components": {...} },

  "db_driver": "mysql", "app_version": "2.8.9", "app_env": "production",
  "time": "2026-07-25 12:00:00"
}
```

**补充：快速健康信息（health/static）**

**路由：** `GET /api/health/static`（Controller：`MainController::healthStatic()`）

### 5.3 映射管理
**核心表：** `ci_job_git_map`
**管理接口：** `/api/admin/job_git_map`（GET/POST/PUT/DELETE）
**认证接口：** `/api/main/map/list`（按 Git 仓库分组，需 Token 认证）

#### 5.3.1 数据写入
- **手动新增/编辑：** 管理后台 UI → AdminController CRUD
- **自动发现：** `POST /api/admin/discover` → `AutoDiscover::discover()` 扫描 Jenkins 所有 Job，分析 SCM 配置提取 Git 仓库 URL → `saveDiscovered()` 写入 `ci_job_git_map`

#### 5.3.2 数据读取与分组
`MainController::mapList()` 的逻辑：

1. 读 `ci_job_git_map` → 过滤 `status=active` → 按 `build_mode` 过滤
2. 按 `job_name` 或 `current_path` 或 `git_remote` 提取 key 分组
3. 每个分组包含：`git_platform`, `git_remote`, `project_id`, `web_url`, `harbor_repository`, `jobs`
4. 写入 `cache` 表（30s TTL），减少重复请求开销
5. `gitlab_ci` 模式下跳过缓存（避免 Jenkins 旧数据污染）

#### 5.3.3 MappingManager 的角色
所有业务层查询必须通过 `MappingManager`：
- `activeMaps()` — 返回当前 `build_mode` 下所有活跃映射
- `resolveProject(path)` — 根据项目路径解析出 `[provider, projectId]`
- `usedGitPlatforms()` — 收集活跃映射中使用的 Git 平台
- `activeJobNames()` — 返回活跃 Job 名列表

#### 5.3.4 Git 平台自动检测
当 `git_platform` 未显式填写时，系统按以下规则自动检测：

1. 提取 `git_remote` URL 的域名
2. 用各 `GitProvider::matchUrl()` 匹配（关键词：gitlab/github.com/gitee.com/...）
3. 如果匹配失败 → 回退到 `DEFAULT_GIT_PLATFORM` 环境变量

### 5.4 构建系统双通道
**模式：** jenkins / gitlab_ci / gitea_ci（多选集合）
**路由统一入口：** `/api/build/{path}/...`

#### 5.4.1 项目解析
所有 Build 操作的第一步是 `resolve(path)`：

```
MappingManager::resolveProject(path)
├─ 遍历 ci_job_git_map，匹配 job_name 或 current_path
├─ 返回 build_provider（jenkins/gitlab_ci）
└─ 返回 projectId（jenkins=path, gitlab_ci=project_id 或 path）
```

#### 5.4.2 BuildProvider 接口
```php
interface BuildProviderInterface {
    public function getName(): string;          // 'jenkins' 或 'gitlab_ci'
    public function trigger(string $projectId, string $ref, array $variables): array;
    public function getPipelines(string $projectId, int $limit = 20): array;
    public function getJobs(string $projectId, int $pipelineId): array;
    public function getJobTrace(string $projectId, int $jobId): string;
    public function getVariables(string $projectId): array;
    public function retry(string $projectId, int $pipelineId): array;
    public function cancel(string $projectId, int $pipelineId): array;
}
```

#### 5.4.3 触发构建 (trigger)
**路由：** `POST /api/build/{path}/trigger`

参数合并优先级：POST body 根级 > POST body `variables` 嵌套 > Query String
如果只有 `ref` 没有其他参数，自动转为 `{branches: ref}`。

#### 5.4.4 Pipeline 列表 (pipelines)
**路由：** `GET /api/build/{path}/pipelines?list=id|build|time|success`

`list` 参数说明：
- `id` — 返回 `[10, 9, 8]` 所有 pipeline 编号
- `success` — 同上，但只返回成功的
- `build` — 返回 `["#10", "#9"]` 成功的 pipeline
- `time` — 返回 `["#10 [2026-07-25]", "#9 [...]]"` 成功 + 时间
- 不传 — 返回完整 JSON（含 build_provider, project_id, pipelines 数组）

#### 5.4.5 可失败点
| 问题 | 原因 | 表现 |
|---|---|---|
| `Build 系统 'xxx' 未配置` | build_mode 与 Provider 实际可用性不一致 | 400 |
| 项目解析失败 | `ci_job_git_map` 中无此项目映射 | 回退到 path 本身作为 projectId |
| Jenkins 504 超时 | `BUILD_TIMEOUT` 过小或网络慢 | 500 |

### 5.5 扫描同步（scan-sync）
**路由：** `POST /api/build/{path}/scan-sync`
**方法：** `BuildController::scanSync()`

**业务流程：**

```
1. 查 ci_job_git_map 获取 harbor_repository + build_provider + git_platform
2. 解析 harbor_repository（格式 project/repo）
3. 从 Harbor 获取 tag 列表
   ├─ body 有 tag → 校验是否在列表中
   └─ body 无 tag → 取列表第一个（最新）
4. 尝试获取最新 pipeline 的 SHA 和 IID（失败不影响主流程）
5. Harbor 扫描报告获取
   ├─ Harbor 不可达 → state=pending
   ├─ 扫描未启用 → state=pending
   ├─ 有漏洞 → state=failed, 记录漏洞数量
   └─ 无漏洞 → state=success
6. Commit Status 回写（通过 Git Provider，不依赖 CI 系统）
   └─ context='harbor-scan', description='#10 → v1.0 · 3 vulns'
7. 记录到 ci_pipeline_artifacts（provider + project_id + pipeline_iid + project_key + repository + tag + status）
```

**⚠️ 关键限制：**
- 必须已配置 `harbor_repository`（否则 400）
- `tag` 必须在 Harbor 中实际存在（严格校验，Harbor 不可达时降级放行）
- `harbor_repository` 格式必须为 `project/repo`（以 `/` 分隔的两段）

### 5.6 Commit Status 回写
**路由：** `POST /api/build/{path}/commit-status`
**方法：** `BuildController::commitStatus()`

**适用场景：** CI pipeline 中任意安全扫描步骤，如 Gitleaks 密钥扫描、Trivy/Snyk 依赖漏洞、SonarQube SAST。

**必填参数：**

| 参数 | 说明 |
|---|---|
| `sha` | Commit SHA（40 位 hex） |
| `state` | pending / success / failed / error |
| `context` | 检查名称，如 "secret-scan"、"sast" |
| `description` | 简短描述 |

**可选参数：**

| 参数 | 说明 |
|---|---|
| `target_url` | 详情链接（如 SonarQube 报告地址） |
| `check_type` | 审计分类标签，默认等于 context |
| `tag` | 关联的镜像 tag |

**执行流程：**

```
1. 参数校验（sha/state/context/description 必填，state 合法性检查）
2. 查 ci_job_git_map 获取 git_platform
   └─ 未配置 → 400 "未配置 git_platform，无法回写"
3. Git Provider 匹配
   └─ 未注册 → 400 "Git 平台 xxx 未配置或不可用"
4. 调用 GitProvider::setCommitStatus(sha, state, context, description, target_url)
   ├─ GitLab: POST /api/v4/projects/{id}/statuses/{sha}
   ├─ GitHub: POST /repos/{owner}/{repo}/statuses/{sha}
   ├─ Gitee:  POST /api/v5/repos/{owner}/{repo}/statuses/{sha}
   └─ Gitea:  POST /api/v1/repos/{owner}/{repo}/statuses/{sha}
5. 记录到 ci_pipeline_artifacts（有 tag 时）
6. 写入 ci_security_checks 审计表（UPSERT，按 project+sha+check_type 唯一）
7. 返回结果（含 git_platform, commit_status 子对象）
```

**COMMIT STATUS 回写不依赖 CI 系统**，只依赖 Git 平台配置。Jenkins 项目也能通过此端点回写 commit status。

### 5.7 安全扫描审计

**数据来源：** `ci_security_checks` 表（由 commit-status 和 scan-sync 写入）

**筛选参数：**
- `project` — 模糊匹配（LIKE %...%）

### 5.9 构建模式切换
**路由：** `GET /api/admin/build_mode` + `PUT /api/admin/build_mode`
**方法：** `AdminController::getBuildMode()` / `updateBuildMode()`

**存储：** `ci_app_settings` 表
- key=`build_mode`，value = {jenkins, gitlab_ci, gitea_ci} 的逗号分隔集合（控制 pull-based CI）
- key=`custom_push_enabled`，value ∈ {0,1}（独立布尔开关，控制 push-based CI）

> **正交设计：** `build_mode`（启用的 pull CI 集合，如 jenkins/gitlab_ci/gitea_ci）仅控制 pull-based CI 通道；`custom_push_enabled` 是独立的布尔开关，两者互不依赖，可同时启用。`build_mode` UI 渲染已配置 CI 的多选框（含「全选」），`custom_push_enabled` 独立勾选。详见 [§5.10](#510-custom_push-自定义推送-ci-模式)。

**读取逻辑（AppConfig::getBuildModes()）：**
```
1. 读 ci_app_settings WHERE setting_key='build_mode'
2. 有值 → 解析逗号分隔集合（旧值 `both` → jenkins,gitlab_ci）→ 返回，source='database'
3. 无值 → 读 app.env BUILD_MODE 种子写入 DB → 返回，source='env'
4. DB 异常 → 降级到 app.env，source='env'
```

**写入校验（前后端一致）：**
- `modes` 必须是 {jenkins, gitlab_ci, gitea_ci} 的子集
- 启用 `jenkins` → 要求 JENKINS_BASE_URL 已配（否则 400）
- 启用 `gitlab_ci` → 要求 GITLAB_BASE_URL + GITLAB_TOKEN 已配（否则 400）
- 启用 `gitea_ci` → 要求 GITEA_BASE_URL + GITEA_TOKEN 已配（否则 400）

**DI 容器行为（container.php）：**
- 不再根据 `BUILD_MODE` 判断是否注册 Provider
- Jenkins / GitLab CI / Gitea Actions 各自检查配置非空就注册
- 实际路由分发由 `MappingManager::activeMaps()` 根据 DB 中的 `build_mode` 集合过滤

**影响范围：** 模式切换只影响映射列表过滤和健康检查中的 Jenkins 检测。

### 5.10 认证与授权
#### 5.10.1 登录
**路由：** `POST /api/admin/login`
**方法：** `AdminController::login()`

**验证优先级：**
1. 查 `admin_users` 表，`password_verify()` 验证 bcrypt hash
2. `app.env` 兜底仅限 `admin_users` 表为空（首次部署）这一种场景；DB 不可访问时登录接口直接报错。其他情况一律不认 `app.env` 密码，忘记密码走离线补丁，获取补丁请联系作者。
3. 认证成功 → 生成 64 位 hex token → 写入 `cache` 表（`admin_token_{token}`，24h TTL）
4. 同时通过 `TokenService::loadPermissions()` 预加载用户权限到 request attribute

> **说明：** 这套 `app.env` 只用于 PHP API 全局管理员回退逻辑。要为 CD 服务创建独立用户，请在后台创建账号并赋予 CD 权限，再写入该 CD 服务自身的 `app.env`（前提是该服务支持它）。

#### 5.10.2 Token 验证（AuthMiddleware + TokenService）
**中间件：** `AuthMiddleware`（应用于 `/api/health`、`/api/health/static`、`/api/main`、`/api/admin`（login/logout 除外）、`/api/build`、`/api/git`、`/api/harbor` 路由组）
**服务：** `TokenService`（封装 token 验证、权限加载、token 撤销）

```
1. 从 Authorization: Bearer xxx 提取 token
2. 调 TokenService::validate() 查 cache 表验证 token（key=admin_token_{token}, expires_at > now）
   ├─ 命中（交互式登录会话）→ 调 TokenService::loadPermissions() 查询角色权限
   └─ 未命中 → 回退 TokenService::validateApiToken() 验证 API Token，
      命中后经 ApiScopeResolver 解析该路由所需 scope：
      ├─ null（如 /api/admin/*）→ 403（fail-closed，管理端点禁止 API Token）
      ├─ 缺失所需 scope → 403（记入 API 调用审计日志）
      └─ 通过 → scope 映射为控制器内二次校验所需权限
3. 将 currentUser、currentRole、userPermissions 写入 request attribute
4. 如果 DB 不可用且 app.env ADMIN_PASSWORD 为空 → 放行（首次启动无密码场景）
5. 如果 DB 不可用且 admin_users 表为空 → 放行
6. 其他 → 401
```

**密码修改时：** `TokenService::revoke()` 删除 cache 表中所有旧 token，强制重新登录。

#### 5.10.3 文档页面认证
**Swagger UI (`/api/docs`) 和 OpenAPI JSON (`/api/openapi.json`)：**
- 使用 routes.php 闭包中的 `$checkAuth`，独立于 `AuthMiddleware`
- 如果 `app.env` 中 `ADMIN_PASSWORD` 为空 → 直接放行
- 否则验证 token（支持 Bearer 或 Query String `?token=`）

#### 5.10.4 Build/Git/Harbor 接口认证（v2.4.3 新增）
`/api/build`、`/api/git`、`/api/harbor` 三个路由组已纳入 `AuthMiddleware` 认证保护。调用这些接口时必须在请求中携带 `Authorization: Bearer <token>` 头。

**认证链路：**
```
Client → CI:  Authorization: Bearer <ci_user_token>   ← 用户 token，CI 验证
CI → GitLab:  PRIVATE-TOKEN: <gitlab_api_token>       ← CI 自己的服务 token
CI → Harbor:  Basic Auth: admin:password               ← CI 自己的服务凭证
CI → Jenkins: Basic Auth: user:api_token               ← CI 自己的服务 token
```

> 下游服务（GitLab/Harbor/Jenkins）使用独立的服务账号认证，不接收 CI 用户 token。这是标准的 BFF/网关模式，确保用户 token 不会泄露到下游日志。

#### 5.10.5 RBAC 权限系统（v2.4，数据驱动）
系统采用基于角色的访问控制（RBAC），**全部表存数据库，可通过后台 UI 直接管理**（新增 CD 菜单时无需改代码）。

| 表名 | 用途 |
|---|---|
| `roles` | 角色定义：`id`, `name`, `description`, `is_system`, `created_at` |
| `permissions` | 权限目录：`perm_key`（点/中划线，如 `cd.deploy.k8s` / `cd.build-manage`）、`description`、`parent_key`、`created_at` |
| `role_permissions` | 多对多关联：`role_id`, `perm_key` |
| `implied_rules` | **权限隐含关系**（独立表）：`source_key`, `target_key` → 拥有 source_key 时自动拥有 target_key |

**系统角色：**
- `super_admin` 是唯一的内置系统角色（`is_system=1`），不可从 UI 编辑或删除
- 权限集为 `'*'` 通配符（定义在 `AppConfig::DEFAULT_ROLES`）
- `seedAdmin()` 创建的 root 用户默认为 `super_admin`

**内置权限目录（DB 初始化种子）：**

| 分类 | 数量 | 键名 |
|---|---|---|
| CI | 8 | `ci.manage`, `ci.users.manage`, `ci.users.manage_admin`, `ci.mapping.edit`, `ci.platform.edit`, `ci.mode.edit`, `ci.discover`, `ci.trigger` |
| CD 一级菜单 | 8 | `cd.build-manage`, `cd.deploy-manage`, `cd.server-manage`, `cd.webshell`, `cd.deploy-record`, `cd.image-registry`, `cd.resource-monitor`, `cd.notification-manage` |
| CD 二级子菜单 | 9 | `cd.deploy.single`/`docker`/`k8s`，`cd.monitor.app`/`system`/`custom`/`alert`，`cd.bot`（机器人配置），`cd.webhook`（WebHook 配置） |

> 注意：**权限命名规范**
> - 一级菜单：`{模块}.{菜单名}`（用中划线，如 `cd.build-manage`）
> - 二级菜单：`{模块}.{分组}.{菜单名}`（用下划线/中划线混合，如 `cd.deploy.single`）
> - 正则校验：`^[a-z][a-z0-9_]*(\.[a-z][a-z0-9_-]*)+$`

**权限隐含规则（正确方向）：**
- 只允许 **子 → 父** 方向（勾选二级菜单自动显示一级菜单）
  - `cd.deploy.*` → `cd.deploy-manage`
  - `cd.monitor.*` → `cd.resource-monitor`
  - `cd.bot` / `cd.webhook` → `cd.notification-manage`
- ❌ **禁止** 父 → 子方向（会导致"保留父菜单时子权限无法取消"的反向依赖 Bug）
- 一条特殊规则：`cd.build-manage` → `ci.trigger`（构建管理隐含触发构建）

**数据库种子与兜底：**
- 首次启动 `seedAdmin()` 会把 `AppConfig::DEFAULT_PERMISSIONS` 和 `IMPLIED_PERMISSIONS` 用 UPSERT 写入 DB
- **读取路径全部走 DB**（权限列表、隐含关系展开、角色权限）；DB 异常时才回退到常量兜底（避免硬故障）
- 后台动态注册的权限同样存 DB；系统内置 key（DEFAULT_PERMISSIONS 中的）受保护不可删
- 新增 CD 菜单权限时：
  - 方式 1（推荐）：后台界面 → 权限注册 → 隐含规则页面加子→父 → 完成（**不改代码**）
  - 方式 2（持久种子）：改 `AppConfig.php` 常量 + 同步 `lang/*/messages.php` 的 `role.perm_{key}` 翻译（点号换下划线），重启后端自动写 DB

**API 端点（v2.4，均在 Swagger UI 的 RBAC 分组下）：**

| 方法 | 路径 | 说明 | 权限要求 |
|---|---|---|---|
| GET | `/api/admin/permissions` | 列出所有权限（`perm_key` + `description` + `parent_key` + `created_at` + `is_builtin`），附 `implied` 关系字典与 `builtin_implied`（内置隐含规则） | Bearer Token + `ci.permissions.list` |
| POST | `/api/admin/permissions` | 注册新权限（body：`{ perm_key, description, parent_key? }`） | super_admin |
| DELETE | `/api/admin/permissions/{perm_key}` | 删除权限（级联清理 role_permissions 和 implied_rules；内置 key 受保护不可删） | super_admin |
| POST | `/api/admin/implied_rules` | 注册权限隐含规则（body：`{ source_key, target_key }`） | super_admin |
| DELETE | `/api/admin/implied_rules` | 删除隐含规则（query：`source_key=&target_key=`；内置隐含规则受保护不可删，用户新增的可删） | super_admin |
| GET | `/api/admin/roles` | 角色列表（含每个角色的 permissions 数组） | Bearer Token + admin 登录 |
| POST | `/api/admin/roles` | 创建自定义角色（body：`{ name, description, permissions }`，传入的 permissions 后端自动展开隐含权限） | `ci.users.manage_admin` |
| PUT | `/api/admin/roles/{id}` | 修改自定义角色（name/description/permissions；is_system=1 不可改） | `ci.users.manage_admin` |
| DELETE | `/api/admin/roles/{id}` | 删除自定义角色（仍有用户绑定此角色时 400 role.in_use） | `ci.users.manage_admin` |
| PUT | `/api/admin/users/{username}` | 更新用户（body：`password` 和/或 `role`） | `ci.users.manage` |
| GET | `/api/admin/me/permissions` | 当前用户的角色 + 权限列表（super_admin 返回 `permissions: "*"` 通配符；其他角色返回已展开隐含的数组） | 仅需有效 Bearer Token |

**API Token 端点（v2.5.0，独立于 RBAC，仅 super_admin）：**

| 方法 | 路径 | 说明 | 权限要求 |
|---|---|---|---|
| GET | `/api/admin/api_tokens/scopes` | 返回可选 scope 目录 | super_admin |
| GET | `/api/admin/api_tokens` | Token 列表（不含明文） | super_admin |
| POST | `/api/admin/api_tokens` | 创建 Token（返回一次性明文） | super_admin |
| POST | `/api/admin/api_tokens/{id}/revoke` | 撤销 Token（软删除，禁用并保留记录） | super_admin |
| DELETE | `/api/admin/api_tokens/{id}` | 删除 Token（硬删除） | super_admin |

> API Token 通过标准 `Authorization: Bearer <token>` 使用，独立于 RBAC，直接携带 scope；`/api/admin/*` 管理端点对 API Token 一律 fail-closed（返回 403）。详见 [API_文档.md](API_文档.md) 的「API Token 管理」章节。

**权限隐含展开逻辑**（`expandPermissions()`）：
```php
// 一次性全量拉 implied_rules 表
foreach ($perms as $pk) {
    if (isset($implied[$pk])) {
        $result[] = array_merge($result, $implied[$pk]);
    }
}
```
实现：DB 主路径，失败回退到 `AppConfig::IMPLIED_PERMISSIONS`。

**权限检查逻辑**（`hasPermission($permKey)`）：
```php
if ($role === 'super_admin') return true;  // 硬编码旁路
// 否则：直接读取 request attribute 中的 userPermissions（由 AuthMiddleware 预加载），
//       expandPermissions() 展开隐含权限，最后 in_array 对比
```
用户的权限数组在 AuthMiddleware 中一次性加载并缓存于 `$this->userPermissions`，一次请求内复用。

### 5.11 Custom_Push 自定义推送 CI 模式
Custom_Push 是一种**推送式 CI** 模式，与 Jenkins/GitLab CI 的**拉取式 CI** 形成互补。用户通过自己的 CI 脚本推送构建状态、日志地址和镜像 tag 到 Devops-Glue，Devops-Glue 仅存储元数据，不参与构建执行也不存储日志内容。

#### 5.11.1 正交设计
| 维度 | build_mode | custom_push_enabled |
|---|---|---|
| 类型 | 拉取式 CI（Pull） | 推送式 CI（Push） |
| 方向 | Devops-Glue → CI 系统 | 用户 CI → Devops-Glue |
| 控制 | jenkins / gitlab_ci / gitea_ci（多选） | 独立布尔开关 |
| 关系 | 互相独立，可同时启用 | 互相独立，可同时启用 |

例如：`build_mode=jenkins,gitea_ci` + `custom_push_enabled=true` 表示 Jenkins + Gitea Actions 拉取式 CI 和 Custom_Push 推送式 CI 同时生效。

#### 5.11.2 核心组件
- **`CustomPushBuildProvider`**（`src/Service/Build/CustomPushBuildProvider.php`）：实现 `BuildProviderInterface`，处理 `trigger`、`getPipelines`、`updateStatus` 等方法。
- **`ci_custom_builds` 表**：存储构建元数据，`(job_name, pipeline_iid)` 为唯一键，`pipeline_iid` 为整数类型。
- **`ci_pipeline_artifacts` 表**：规范 pipeline-artifact 事实，CD 层通过 `GET /api/build/{path}/tag` 读取。

#### 5.11.3 配置注册
通过 `settings.php` 的 `build.custom_providers` 数组配置，默认已配置 CustomPushBuildProvider：

```php
'build' => [
    'custom_providers' => [
        [
            'name'   => 'custom_push',
            'class'  => 'App\\Service\\Build\\CustomPushBuildProvider',
            'config' => [
                'variables' => [
                    'env'       => ['type' => 'choice', 'choices' => ['dev', 'staging', 'prod'], 'description' => '构建镜像目标环境（可选）', 'required' => false],
                ],
            ],
        ],
    ],
],
```

DI 容器（`container.php`）通过遍历 `build.custom_providers` 配置自动注册所有自定义 Provider。

#### 5.11.4 上报接口
**结果上报：`POST /api/build/{path}/report`**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `pipeline_iid` | INTEGER | ✅ | 构建编号（用户 CI 传入） |
| `status` | string | ✅ | `success`/`failed`/`aborted`（终态，无 pending/running） |
| `finished_at` | datetime | ✅ | 构建完成时间 |
| `started_at` | datetime | ❌ | 构建开始时间 |
| `ref` | string | ❌ | 构建分支/tag |
| `sha` | string | ❌ | Commit SHA |
| `exit_code` | INTEGER | ❌ | 构建退出码 |
| `log_url` | string(URI) | ❌ | 日志 URL（仅存指针，Devops-Glue 不存日志内容） |
| `web_url` | string(URI) | ❌ | 用户 CI 构建页链接 |
| `tag` | string | ✅（success） | 镜像 tag，`status=success` 时必填并写入 `ci_pipeline_artifacts` |
| `harbor_repository` | string | — | Harbor 仓库路径，由 `job_git_map` 决定（body 传入被忽略），须为 `project/repo` 两段式；上报时校验仓库与 `tag` 均真实存在于 Harbor（任一不存在返回 400） |
| `env` | string | ❌ | 镜像目标环境（自定义变量，可选） |

> **控制字段**（`pipeline_iid`/`status`/`finished_at`/`started_at`/`ref`/`sha`/`exit_code`/`log_url`/`web_url`/`tag`/`harbor_repository`）以外的字段自动存入 `variables_json`。
> `status=success` 时 `tag` 与可解析的 `harbor_repository` 必填，写入 `ci_pipeline_artifacts`（provider、project_id、pipeline_iid、project_key、repository、tag、status）；重复上报按覆盖（UPDATE）处理。
> 所有 JSON 键使用小写 snake_case。

#### 5.11.5 日志代理
Devops-Glue 不存储日志内容，仅存储 `log_url` 指针。访问构建日志时，系统通过 302 重定向代理拉取日志内容，确保证据链由执行方（用户 CI）持有。

#### 5.11.6 管理面板
- **状态卡片**：系统监测页显示 Custom_Push 状态 ✅（已配置）或 ⚪（未配置）
- **自动发现**：`AutoDiscover` 扫描 Git 平台时，若 `custom_push_enabled=true`，自动识别 `build_provider=custom_push` 的项目
- **多选框**：`build_mode` 多选框（jenkins/gitlab_ci/gitea_ci + 全选）只显示已配置的 CI
- **刷新要求**：前端变更后需浏览器硬刷新（Ctrl+F5），配置/控制器变更后需后端重启

#### 5.11.7 权限与 Scope
report 接口复用 `build.report` scope，通过 API Token 的 `Authorization: Bearer <token>` 头鉴权。

### 5.12 安全加固（响应头 / 审计日志）
**统一安全响应头**（`config/docker/nginx.conf`）：`X-Frame-Options: DENY`、`X-Content-Type-Options: nosniff`、`Referrer-Policy: no-referrer`、`Permissions-Policy`（关闭摄像头/麦克风/定位等）、以及 CSP：

```
default-src 'self'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline';
img-src 'self' data: blob:; font-src 'self' data:; connect-src 'self';
object-src 'none'; frame-ancestors 'none'; base-uri 'self'; form-action 'self'
```

- `'unsafe-inline'` 目前无法去掉：`admin.html` 有大量内联 `onclick` 与内联 `style`。第一方 JS 已确认无 `eval` / `new Function`，故未放开 `unsafe-eval`。后续把内联 handler 抽成外部事件绑定后可收窄为 `script-src 'self'; style-src 'self'`。
- ⚠️ **改 nginx 头时注意继承语义**：子级（`location` / `if`）**一旦出现任何 `add_header`，父级 `server` 级的 `add_header` 会被整体丢弃**，不叠加。静态资源 location 因有 `add_header Cache-Control`，必须把 5 个安全头原样重复一遍（文件内以「安全头组」注释标记，改一处务必同步改另一处）。
- HSTS 仍随 HTTPS 块注释保留，启用 HTTPS 后再放开。

## 6. 关键数据流

### 6.1 构建 → 扫描 → 回写 完整链路

```
CI Pipeline 触发
    │
    ├── 构建 Docker 镜像 → Push 到 Harbor
    │
    ├── 安全扫描步骤（Gitleaks / Trivy / SonarQube）
    │   │
    │   └── POST /api/build/{project}/commit-status
    │       ├─ sha={SHA}, state=failed/success
    │       ├─ context=secret-scan, check_type=secret-scan
    │       ├─ → Git Provider setCommitStatus() 回写
    │       └─ → ci_security_checks 表记录
    │
    └── Harbor 扫描同步
        │
        └── POST /api/build/{project}/scan-sync
            ├─ 查 Harbor 扫描报告（漏洞数量）
            ├─ → Git Provider setCommitStatus(context=harbor-scan)
            └─ → ci_pipeline_artifacts 记录 tag→pipeline 映射
```

### 6.2 映射配置 → API 调用 链路

```
管理后台编辑映射
    │
    └── AdminController CRUD
        └── AppConfig::saveJobGitMap()
            └── ci_job_git_map 表全量写入

API 调用（如 /api/build/project/tag）
    │
    └── BuildController → resolve(project)
        └── MappingManager::resolveProject(project)
            └── 遍历 ci_job_git_map 匹配 job_name/current_path
                ├─ 返回 build_provider → BuildProviderRegistry::create()
                └─ 返回 git_platform → GitProviderRegistry::create()
```

### 6.3 构建模式切换生效链路

```
管理后台: PUT /api/admin/build_mode {mode: "jenkins"}
    │
    └── AdminController::updateBuildMode()
        ├─ 校验 Provider 可用性
        └── AppConfig::setBuildMode("jenkins")
            └── ci_app_settings UPSERT {key:"build_mode", value:"jenkins"}

下一次 API 调用:
    │
    └── MappingManager::activeMaps()
        └── AppConfig::getBuildMode() → "jenkins"
            └── 只返回 build_provider != 'gitlab_ci' 的映射
```

## 7. 常见故障排查

### 7.1 数据库相关

| 症状 | 可能原因 | 排查方法 |
|---|---|---|
| 启动报 `DB_DRIVER 必须设为 sqlite 或 mysql` | `app.env` 未配或配置错误 | `echo $DB_DRIVER`，确认值正确 |
| SQLite 报 `unable to open database` | 目录无写入权限 | `chmod 777 config/data/` |
| MySQL 报 `Access denied` | 密码错误或用户权限不足 | `mysql -u root -p` 验证 |
| 表不存在报错 | `DB_AUTO_MIGRATE=false` 且未手动建表 | 检查 `app.env` 中 `DB_AUTO_MIGRATE` 值 |
| `admin_users` 表有数据但登录失败 | 密码 hash 与当前记忆不一致 | 用离线补丁重置，获取补丁请联系作者 |

### 7.2 外部服务连接

| 症状 | 可能原因 | 排查方法 |
|---|---|---|
| Jenkins 健康检查返回 false | JENKINS_BASE_URL 不可达 | `curl $JENKINS_BASE_URL/api/json` |
| Git 平台 reachable=false | base_url 不对或网络不通 | `curl -I $GITLAB_BASE_URL` |
| Harbor 检查失败 | Harbor 服务未启动或 URL 不对 | 逐个检查 `/api/v2.0/projects` 等端点 |
| Harbor 扫描 HTTP 503 | Harbor 扫描器未配置 | Harbor 管理后台检查扫描器 |
| Git Provider `setCommitStatus` 返回 404 | `project_id` 错误或无权限 | 检查 Git 平台项目是否存在 |

### 7.3 构建相关

| 症状 | 可能原因 | 排查方法 |
|---|---|---|
| `Build 系统 'xxx' 未配置` | `build_mode` 与 Provider 可用性不一致 | `/api/admin/build_mode` 检查 has_jenkins/has_gitlab_ci |
| 模式切换后构建行为不变 | `ci_job_git_map` 中 `build_provider` 字段未同步 | 检查每个映射项的 `build_provider` |
| Pipeline 列表为空 | Jenkins/GitLab CI 中项目不存在或无 pipeline | 直接访问 CI 系统确认 |
| scan-sync 报 `tag 在 Harbor 中不存在` | tag 已被清理或还没同步 | 确认 Harbor 中存在该 tag |

### 7.4 映射配置

| 症状 | 可能原因 | 排查方法 |
|---|---|---|
| 项目找不到对应映射 | `job_name` 或 `current_path` 不匹配 | `GET /api/admin/job_git_map` 查看全部映射 |
| `git_platform` 自动检测失败 | URL 不含平台关键词 | 手动在映射中指定 `git_platform` |
| mapping 修改后不生效 | 缓存（30s TTL）未过期 | 等待 30s 或重启服务，或切到 gitlab_ci 模式（跳过缓存） |

### 7.5 认证相关

| 症状 | 可能原因 | 排查方法 |
|---|---|---|
| 登录始终 401 | `admin_users` 表密码和 `app.env` 不一致 | 用离线补丁重置，获取补丁请联系作者 |
| Token 突然失效 | 服务重启、密码被修改或 24h 过期 | 重新登录 |
| Swagger UI 无法访问 | 未登录 | 访问 `/api/docs` 会自动跳转登录页 |

### 7.6 性能相关

| 症状 | 可能原因 | 解决方法 |
|---|---|---|
| `/api/health` 响应慢（>3s） | 外部服务超时 | 降低 timeout 值（默认 3-5s），检查网络 |
| 映射列表接口慢 | 缓存未命中 + DB 查询慢 | 确认 cache 表存在且有写入权限 |
| Harbor 分页请求大量数据 | 项目/仓库/tag 数量多 | 分页上限已设（projects 1000, repos 1000, tags 2000），超限记录 warning 日志 |
