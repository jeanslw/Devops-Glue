# Changelog

## v2.8.9 (2026-10-11)
- **Manual schema mode (`DB_AUTO_MIGRATE=false`) and migration-failure attribution** — How the schema gets created is now an explicit choice: auto mode (the app account runs DDL) or manual mode (run `database/*.sql` yourself, then align the schema with a privileged account). `schema_version` (table structure / DDL) is split from the new `seed_version` (RBAC seed): in manual mode the app writes no `schema_version`and no longer re-runs `seedRbac()` on every php-fpm request (short-circuited by `seed_version`), and it never reports "seed applied" as "schema aligned". A new `cli/migrate.php` takes the same `Database::migrateNow()` path as the web "Sync Schema" button but **ignores** `DB_AUTO_MIGRATE`, so a deployment pipeline (K8s Job / initContainer, Helm pre-upgrade hook, one-shot Compose service) can create tables / back-fill columns with a privileged account while the runtime account stays DML-only (least privilege). `/healthz` is now a two-stage probe: `db` only reports connectivity — unreachable (down / bad credentials) or connected but version table missing (uninitialised DB) → **503** + `status=degraded`; reachable with `schema_current=false` (the expected "new code + old schema" rolling-upgrade state) → **200** + `status=degraded` so the LB / K8s does not pull every replica; the payload adds `seed_version` / `schema_current` / `auto_migrate` and only probes table by table (returning `tables_missing`) once it is confirmed out of date, and failure branches now log errors instead of silently swallowing them. The "Sync Schema" button runs DDL with the **application's own database account** and, when that account lacks `CREATE` / `ALTER` (attributed by `Database::classifyMigrationError()`, covering MySQL 1044/1142/1227 and SQLite read-only databases while never misclassifying a 42000 syntax error / a 1060 re-run as a privilege issue), answers **409** with an actionable hint (use `php cli/migrate.php`, or temporarily set `DB_AUTO_MIGRATE=true` and restart) plus a failed operation-log entry, instead of a vague 500; `cli/db-init.php` attributes its failures the same way (check connection settings, or run the init script / CLI). The front-end toast gains a `warn` (amber) state separating an actionable warning from a real failure, and the terminology is unified as "Sync Schema". The CN/EN docs, OpenAPI (CN/EN), the `DatabaseBootstrapTest` unit tests and the smoke test are synced.
- **Migration observability and seed-robustness hardening** — (1) **`php cli/migrate.php --dry-run`**: a read-only pre-check that prints the tables/columns that would be added plus the version state and **writes nothing** (under SQLite a missing database file is still created empty); exit codes 0 = nothing to migrate, 2 = migration needed, 1 = fatal, so a pipeline can decide before it acts. The column list was extracted from `ensureTables()` into `Database::columnMigrations()` and is now **shared** with the new `pendingChanges()` pre-check, so the preview and the real run can never drift; the pre-check needs **no DDL privileges**, so even the minimal-privilege runtime account can run it. (2) **Downgrades (rollbacks) now seed in merge mode**: when the recorded version is higher than the code version, `seedRbac()` becomes **add-only** — mappings the new version granted are kept while mappings the current code expects are added — so a rollback can no longer silently narrow system-role permissions; an explicit `cli/migrate.php` / button run always **converges** to the current code definitions (prune): "an explicit action is the authoritative seed". (3) **Version transitions are now audited in the operation log**: the automatic bootstrap path records `schema_init` / `schema_upgrade` / `schema_downgrade` by direction (results success/success/failure; `detail` carries `scope(schema|seed)`, `previous`/`current` and `seed_mode`), while explicit paths record `migrate_schema` — **`cli/migrate.php` previously left no trace at all in the UI and now logs `from → to` with `channel=cli`**; the operator is always `system`, and the same `(action,target)` is deduplicated within a 10-minute window (web/worker processes starting up do not spam it). (4) **`/healthz` gains the direction flag `schema_ahead`**, separating "the structural migration never ran" from "the code was rolled back" (versions compared with `version_compare`, not lexicographic order). (5) **Partial seed failures now fail fast**: any failed row write inside `seedRbac()` (permissions / implied rules / system roles / role-permission inserts or pruning) is **collected and thrown** (the same mechanism as `verifySeed()`) — the version marker is not advanced, the next boot retries and self-heals, and both the file log and the operation log (`rbac_seed_failed`) are written; it deliberately no longer "logs and continues", which could hide a half-seeded RBAC as a long-running feature bug. Chinese/English docs (two new FAQ entries: rollback/downgrade guidance and "RBAC seed partially failed"), OpenAPI (CN/EN), unit tests and the smoke test are synced.
- **Explicit-migration downgrade auditing and an audit-dedupe-key fix** — After a rollback, running \"Sync Schema\" / `cli/migrate.php` with the old code (the alignment step of the rollback SOP) pulls the version markers back and prunes system-role permissions to the old code's definitions — until now this **directional fact was completely invisible in the operation log** (all you saw was a successful `migrate_schema`). It is now recorded: a file WARNING plus a `schema_downgrade` audit row (`detail.channel=explicit_migrate`, `seed_mode=prune`, distinguishing it from the bootstrap path's merge semantics; when both `schema_version` and `seed_version` are ahead the two are aggregated into one row with `target` = the highest downgraded version). The audit dedupe key is also widened from `(action,target)` to `(action,target,channel)`: downgrade events from the automatic bootstrap (`channel=bootstrap`) and from an explicit migration (`channel=explicit_migrate`) **no longer dedupe each other** — merge (keeps permissions) and prune (narrows permissions) have different consequences and both must stay visible; within the same channel the 10-minute dedupe window still applies. Also documented as a known edge case: php-fpm workers starting concurrently in the same second may produce a one-off duplicated audit row (at most one per worker). The admin \"System Info\" panel gains a **\"Migration Mode\"** row right under \"Schema Status\": it renders the auto/manual semantics according to the effective `DB_AUTO_MIGRATE` value (e.g. \"Manual (tables via database/*.sql or cli/migrate.php; app only seeds)\"; manual is amber, hinting that provisioning DDL is on the operator), backed by a new `auto_migrate` boolean field on `GET /api/admin/system_info`. CN/EN docs and the `DatabaseBootstrapTest` unit tests are synced.
- **Removed the never-consumed `/api/rbac/users/{username}/verify-password` endpoint** — The password-verification oracle (rate-limited and root/`super_admin`-excluded since v2.8.1) turned out to have zero callers: the CD backend verifies its own account passwords locally (bcrypt/argon2id auto-detect) and its git history contains no call to this endpoint, making it dead code whose only value was as a brute-force surface. The route, controller method, rate-limiter helpers, the controller's now-unused `\PDO` dependency, the scope test entry, OpenAPI (CN/EN) and the API docs are all removed, eliminating the attack surface outright; `rbac.user.write` still covers the remaining create / read / update / delete / role-catalog endpoints, and CD login (via `POST /api/admin/login`) is unaffected.
- **Schema-version SQL literals moved to parameter binding** — The schema-version lookups in `Database::isSchemaCurrent()` / `Database::schemaStatus()` and `/healthz` concatenated the `SCHEMA_VERSION_KEY` constant into the SQL string. A constant is not injectable, but the safety relied on convention rather than mechanism; all three are now prepared statements with bound parameters, matching the parameterized style used everywhere else (table-name interpolation stays, as PDO cannot bind identifiers).
- **Unauthenticated `/healthz` liveness/readiness probe** — A new public `GET /healthz` returns database reachability plus `app_version` / `schema_version` in milliseconds (it does not probe Jenkins/Git/Harbor). It answers **503 + `status=degraded`** when the DB is unreachable (reported truthfully, never 500) so Uptime Kuma / cloud load balancers / container orchestration can monitor it. It reuses the existing schema-version record in `ci_app_settings`; the smoke test and OpenAPI (CN/EN) are synced. The global CORS middleware no longer resolves `Settings` → `PlatformVersionRepository` → `\PDO` at construction (it reads the pure `cors` config array directly), so a DB outage can no longer turn the probe's own 503 into a 500 before the handler runs.
- **Container hardening** — The `devops-glue` service now runs with `cap_drop: ALL` plus `security_opt: no-new-privileges`, re-adding only the capabilities the root supervisor genuinely needs (`NET_BIND_SERVICE` for nginx `:80`, `CHOWN`/`FOWNER`/`DAC_OVERRIDE` for the entrypoint's runtime-directory ownership, `SETUID`/`SETGID` to drop nginx/php-fpm workers to `www-data`, and `KILL` for master→worker signal management), stripping `NET_RAW`/`SYS_CHROOT`/`MKNOD`/`SETFCAP` and the rest.
- **`config/app.env.local` no longer baked into the image** — `.dockerignore` listed `app.env.local` without the `config/` prefix, so the local override file (real GitLab/GitHub/Gitee/Gitea/Harbor/Jenkins tokens and admin/DB passwords) was being copied into the published image and silently overriding the host-mounted `config/app.env` at runtime; the entry is corrected to `config/app.env.local`, so it stays host-mounted only.
- **Centralized password hashing + argon2id option** — All password writes (seed, create-user, change/reset password, RBAC, offline `reset-admin.php`) now go through a single `PasswordHasher`; `PASSWORD_HASH_ALGO` selects `bcrypt` (default, explicit cost 12) or `argon2id` (64 MiB / time 4 / threads 1) for **new** hashes. `password_verify()` auto-detects the algorithm, so existing bcrypt hashes keep verifying with no migration; bcrypt stays the default because argon2id allocates 64 MiB per verify.
- **Legacy base64 doc token disabled by default** — The old `base64(user:password)` token accepted for `/docs` access is now gated behind `ADMIN_LEGACY_TOKEN` (default **off**): it never expires, cannot be revoked, and equals a plaintext credential, whereas the modern random token (sha256-stored in the `cache` table) already covers docs access. Enable it explicitly only if an old Swagger client still depends on it.
- **Front-end DOM XSS hardening** — Two `innerHTML` sinks interpolated unescaped values: the breadcrumb's home link put `adminRootPath()` (derived from `location.pathname`) straight into `href`, and the monitor page's service-name header reused `data-base` / `textContent` as raw HTML. Every dynamic value (admin root path, route key, icon, translation, and the service-name base text) now passes through `esc()` before reaching `innerHTML`, closing the CodeQL "DOM text reinterpreted as HTML" and "client-side cross-site scripting" findings in `breadcrumb.js` / `monitor.js`.
- **GitHub Actions minimum permissions** — All four workflows now declare explicit `permissions` instead of inheriting the default read/write `GITHUB_TOKEN`: `ci.yml` and `security.yml` drop to `contents: read` (both are read-only), `docker-publish.yml` scopes its publish job to `contents: read` + `packages: write`, and `release.yml` keeps only `contents: write`; every `uses:` action is additionally pinned to a commit SHA. This closes the CodeQL "workflow does not contain permissions" findings.
- **Versioning** — `APP_VERSION` bumped to 2.8.9; OpenAPI `version` synced (CN/EN).

## v2.8.8 (2026-10-05)

- **Mapping management rework (auto-discovery refactor)**
  - "Git platform" returns to its pure Git-hosting meaning: platforms without a native CI integration (e.g. Bitbucket) are discoverable too; the Git-platform scan is no longer gated by the custom_push switch and labels projects by the platform's native CI (GitLab projects → `gitlab_ci`, Gitea projects → `gitea_ci`; only platforms without a native pull-based provider fall back to `custom_push`).
  - Any Git project can have its CI source manually changed to custom_push; the option is unavailable only when custom_push itself is disabled.
  - Mappings whose provider is disabled are always shown in the management list (fixing the previous "there one moment, gone the next" caused by asynchronous front-end filtering); activating one is blocked with a prompt to change the CI source or enable the corresponding build mode. The CD build page still lists only mappings of enabled providers.
  - Jenkins platform identification corrected: a hint table is built from the same-scan GitLab / Gitea platform results, and Jenkins jobs first look up the real platform by repository path — fixing the mislabeling as GitLab when the host is the same but port/protocol differ (Gitea 3000/222, GitLab 8082/2222).
  - Dedup now covers all built-in providers (jenkins / gitlab_ci / gitea_ci records always included; custom_push records included per its switch), eliminating cross-scan duplicate suggestions.
- **PHPStan raised to level 8 (maximum)** — The static-analysis level was raised stepwise from 5 to 8: 50+ files gained array generic annotations; a new `PdoPrepareReturnTypeExtension` (based on the project-wide PDO `ERRMODE_EXCEPTION` invariant) declares prepare/query to return `PDOStatement` rather than `PDOStatement|false`; it lives in the `phpstan/` directory and is loaded only via autoload-dev, never entering the production autoload. `Database` gains a `pdo()` accessor removing the nullable static property and throwing an explicit exception when not bootstrapped; `json_encode` / `getParsedBody()` / list returns were narrowed point by point, with no ignores or baseline. CI now uses the composer-locked `vendor/bin/phpstan` (single source of truth for the version) and drops the .gitignored `bin/` analysis path.
- **API access-log dual writes unified** — File-log and database-table writes are now both controlled by the `api_access_log_level` switch (previously the file log was ungated and wrote everything); route-template resolution now uses Slim RouteContext, fixing route matching in audit records.
- **Menu grouping and UI polish** — The admin sidebar is grouped into 4 sections; the landing page supports the browser immersive-reader mode (not triggered on login pages); the topbar account menu i18n is completed; mobile issues (table overflow, vertical pagination text, wrapping build-mode values) are fixed; pull-record tables keep a persistent header (title columns render first while loading); push-record headers are translated to Chinese and aligned with pull records (SHA → COMMIT, menu name unified to "Push Records"); topology-graph link colors are unified.
- **Three read-only audits in the admin "Log Center"** — The standalone "Operation Logs" menu becomes a "Log Center" group with three read-only sub-items: **Operation Logs**, **Deploy Logs** and **API Access Logs**. The Deploy Logs list shows CD deployment records for auditing (time, project, tag, image, deploy type, target, status, triggered by, note) — no detail view, no large `output`/`stage_times` columns. It reads the CD-owned `v_glue_deploy_logs` contract view only (never `cd_deploy_logs` directly), defaults to the last 30 days, supports filtering by project / status / deploy type / date, and degrades gracefully to a placeholder when the view is missing or CD is disabled. The API Access Logs record only API-token-authenticated requests (interactive sessions are not recorded), with audit fields such as token display name (never the token itself) / call time / result / failure reason; request body/query are never returned.
- **Permissions** — New `ci.logs` (Log Center parent), `ci.deploy-logs` (Deploy Logs read-only) and `ci.api-logs` (API Access Logs read-only) permissions, seeded into `DEFAULT_PERMISSIONS` / `IMPLIED_PERMISSIONS` (child→parent) / the `viewer` role so they show up in role management; `ci.operation-logs` is re-parented under `ci.logs`. `GET /api/admin/deploy_logs` is gated by `ci.deploy-logs`, and `GET /api/admin/api_access_logs` by `ci.api-logs`.

## v2.8.6 (2026-09-23)
- **Fix: `app.env.local` / `app.env.{APP_ENV}` overrides had no effect** — The override layers used `Dotenv::createUnsafeImmutable()`, but phpdotenv's Immutable means "do not write if the variable already exists" (`RepositoryBuilder::make()` → `ImmutableWriter`), so every key already defined in `config/app.env` (`DB_DRIVER` / `HARBOR_*` / `APP_DEBUG`, ...) was silently dropped — the symptom being "editing `config/app.env.local` does nothing". The override layers now use `createUnsafeMutable()`, and the new `src/Support/EnvFileLoader.php` collapses the five duplicated loader blocks (Bootstrap + bin/cli scripts) into a single implementation. Effective priority: `app.env.local` > real environment variables (Docker `env_file` / shell / `SetEnv`) > `app.env.{APP_ENV}` > `app.env`; when `app.env.local` exists, the keys it defines are final. Real environment variables are written back from a `getenv()` snapshot after the override layers, which also fixes OS-injected variables being shadowed by `app.env` when `variables_order` lacks `E`/`S` (or when values come from `putenv()`).

- **On-demand tag jobs from the admin panel** — The "Clean up stale tag records" and "Image tag log backfill" cards on System Settings → Platform Config now expose **▶ Clean up now** / **▶ Backfill now** buttons, so deployments without cron or CLI access (shared hosting) can run either job immediately instead of waiting for the next cycle. They call `POST /api/admin/tag_cleanup` / `POST /api/admin/tag_backfill` and reuse the exact same `PipelineTagService` path and safety invariants as the CLIs: a 409 refusal (and a greyed-out button) when the matching switch is off or Harbor is unconfigured, rows with an unreachable Harbor or incomplete info are always skipped, missing tags are only filled in and scan results are never overwritten. The run is idempotent and repeatable, shows the stats inline and records them in the operation log (`cleanup_pipeline_tags` / `backfill_pipeline_tags`); permission stays `ci.platform-config`.

- **Docs & screenshots synced from 2.8.5** — Architecture (CN/EN), deployment-config manual, admin manual, README (CN/EN), FAQ and the system screenshots are brought back onto the standard line, so the standard documentation covers the distributed-deployment split (single-image/two-role containers + distributed timer lock) too. `API_Documents.md` is renamed to `API_Reference.md` and all references updated.
- **Versioning** — `APP_VERSION` bumped to 2.8.6 (marks the schema-migration intent); OpenAPI `version` synced (CN/EN).

## v2.8.5 (2026-09-22)
- **Distributed-deployment support (timer split)** — The stateless web layer is now separated from the scheduled timer jobs so it can scale out safely. `supervisord.conf` keeps only nginx + php-fpm; a new `supervisord-worker.conf` runs just `tag-cleanup` / `tag-backfill`, and docker-compose gains a `devops-glue-worker` service that reuses the same `devops-glue:latest` image (same entrypoint, only a different supervisor config bind-mounted onto the same path; no port).
- **Distributed timer lock** — `Database::tryAcquireLock()` / `releaseLock()` add a lease lock backed by the `cache` table (`cache_key` PK), so the timers run at most once across multiple worker replicas (MySQL multi-instance or a shared SQLite file). Acquisition deletes expired leases then does a plain `INSERT` (a PK conflict means the lock is held → exit 0 "skip"); release is token-scoped so a timeout-takeover can't delete the new holder's lease; the lease auto-expires via TTL (600s) so a crashed holder can't deadlock the schedule. Both `cli/cleanup-pipeline-tags.php` and `cli/backfill-pipeline-tags.php` acquire/release the lock around the work phase.
- **Documentation** — Architecture docs (CN/EN) document the single-image/two-role container split and the distributed timer lock.
- **Versioning** — `APP_VERSION` bumped to 2.8.5; OpenAPI `version` synced (CN/EN).

## v2.8.4 (2026-09-20)
- **Image Tag column for pull records** — Pull-type build records (jobs list / pipelines) gain an "Image Tag" column, projected from the harbor-scan writeback success onto `ci_pipeline_artifacts`.

The result is cached in `ci_pipeline_build_log` (`source='log'`) together with the canonical identity (`provider` / `project_id`) and Harbor `repository`, so it can be promoted later without re-resolving the provider.
- **Tag backfill cron** — New `cli/backfill-pipeline-tags.php` and `PipelineTagService::backfillTagsFromBuildLog()` promote log-derived tags into the canonical `ci_pipeline_artifacts`, but only after Harbor explicitly confirms the tag exists; existing canonical tags are never overwritten, and an unreachable Harbor / empty repository or tag are skipped safely. Gated by a new `backfill_tag_enabled` switch (default off).
- **Platform-config consolidation** — The tag-related settings (log keyword, stale-tag cleanup, backfill) moved from `/api/admin/build_mode` to the `ci.system`-gated `/api/admin/platform_config` endpoint, which now also accepts `PUT`.
- **Configurable tag-cron intervals** — The `tag-cleanup` / `tag-backfill` supervisor loops read `TAG_CLEANUP_INTERVAL` / `TAG_BACKFILL_INTERVAL` (seconds, defaults 3600 / 1800) from the container environment, so both schedules are tunable without rebuilding.
- **Image-tag re-parse** — Failed pull records whose tag was derived from the build log now expose a ↻ re-parse action that force-resolves the tag (bypassing the cache), fixing the "wrong previous-build tag" mismatch when the harbor-scan writeback missed.
- **Non-blocking platform-version detection** — The platform-versions page now renders the config table instantly and probes Harbor / Jenkins versions in a separate request, so a slow or unreachable platform no longer freezes the page.
- **Platform-config tag cards** — The three tag settings (stale cleanup / log backfill / log keyword) are split into three side-by-side cards with compact left-aligned toggles.
- **Versioning** — `APP_VERSION` bumped to 2.8.4; OpenAPI `version` synced (CN/EN).

- **Config env files renamed to `*.env`** — Base config `config/.env` becomes `config/app.env`; environment/local overrides are unified to `config/app.env.{APP_ENV}` (`app.env.production` / `app.env.staging` / `app.env.local`). All six loader sites (Bootstrap + bin/cli scripts), `docker-compose.yml`, `.gitignore`, `.dockerignore`, `phpstan.neon.dist` and docs are updated so every config file ends in `.env`. Templates rename accordingly: `config/.env.example` → `config/app.env.example`, `config/.env.staging` → `config/app.env.staging`. PHPStan analysis now also covers the `bin/` and `cli/` paths.
- **Harbor version-probe diagnostics** — `HarborService` emits a debug log line per probed version candidate and an aggregated warning when all probes fail, making an unreachable or wrongly-credentialed Harbor far easier to spot in container logs.

Auto-discovery now scans Gitea repos (`/api/v1/user/repos`) and emits `build_provider=gitea_ci` mappings.
- **Gitea Actions API completeness** — `trigger` (workflow_dispatch with `return_run_details`), `retry` (rerun), `cancel`, and job logs now use the Gitea 1.27 Actions endpoints; the platform-versions page additionally shows the detected Jenkins server version (hidden when Jenkins is unconfigured).

The admin "Configure Mode" page renders checkboxes (Jenkins / GitLab CI / Gitea Actions + Select All) and only shows configured CIs; unchecking a CI demotes its active mappings to Pending.

Covered by the new `BuildStatusTest` regression tests.
- **`/api/main/jobs/list` multi-provider fix** — Removed the Jenkins-first short-circuit that returned only live Jenkins jobs (dropping gitlab_ci/gitea_ci) whenever Jenkins was enabled; the endpoint now merges the active-mapping `job_name`s of the other enabled providers (deduplicated).
- **Build-records RBAC permissions** — Added three permissions: `ci.build-records` (top-level menu) with `ci.build-records.pull` / `ci.build-records.push` (pull / push read-only sub-views), seeded via `DEFAULT_PERMISSIONS` / `IMPLIED_PERMISSIONS` / `DEFAULT_ROLES`; implied rules `pull/push → ci.build-records` and `ci.mapping.edit → ci.build-records.pull` (keeps the mapping page's "Copy Pipeline ID" working). Pull-record read endpoints (`/api/build/jobs/list`, `/pipelines`, `/pipelines/{id}`, `/logs/{id}`, `/pipelines/{id}/logs`) and push records (`/api/admin/custom_builds`, previously gated by the wrong `ci.mode.edit`) now enforce `requirePermission` on the backend; the `build.read` scope maps to `ci.build-records.pull` so CD service accounts reading pull records are not 403'd; the `viewer` read-only role seed grows from 8 to 11 keys.
- **LDAP config completion** — `config/settings.php` gains `LDAP_ATTRS` (comma-separated attributes read back after login, default `uid,cn,mail,dn`, extensible per directory schema e.g. `email`/`sAMAccountName`); `.env.example` and the admin manual's Appendix A now document `LDAP_ATTRS` and the LDAPS self-signed-cert OpenLDAP pass-through vars `LDAPTLS_CACERT` / `LDAPTLS_REQCERT`.
- **Operation-log audit** — New append-only `ci_operation_logs` table and `OperationLogRepository` record every backend write operation and login event (login / login_failed / login_locked / logout / change_password, mapping + platform-version + build-mode changes, user / role / permission / implied-rule / API-token CRUD, and build trigger / retry / cancel) with actor, operator type (`admin` vs `api_token`), target, detail JSON, IP, and result. A new `GET /api/admin/operation_logs` endpoint (gated by the `ci.operation-logs` permission, covered by the super_admin `*` wildcard) serves paginated + filterable logs to a new admin "操作日志" tab. ## v2.8.1 (2026-09-13)
